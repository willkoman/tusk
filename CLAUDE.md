# Tusk — Agent Onboarding

Fast, native, lightweight **Postgres-first database client**. Goal: replace the clunk of pgAdmin and the resource weight of JetBrains DataGrip. Tauri (system WebView, not Electron) + Rust + SolidJS. Launches sub-second, low RAM, ~5 MB installer.

This file is the source of truth for working in this repo. Keep it, `CHANGELOG.md`, and the code in sync.

## Stack

- **Shell:** Tauri v2 (system WebView2 / WKWebView / WebKitGTK — no bundled browser).
- **Frontend:** SolidJS + TypeScript + Vite + CodeMirror 6.
- **Backend:** Rust + `tokio-postgres` (text/simple protocol), `native-tls`, `keyring`; `duckdb`/`rusqlite` embedded, `mysql_async` and `tiberius-ng` (TDS) over the network, `russh` (SSH tunnels).

## Build / run / verify

```sh
npm install                 # once
npm run tauri dev           # run the app (needs Rust + Node 20)

# Validate after edits (ALWAYS do this before claiming done):
cargo fmt --manifest-path src-tauri/Cargo.toml --all -- --check
cargo build --locked --manifest-path src-tauri/Cargo.toml
cargo clippy --locked --manifest-path src-tauri/Cargo.toml --all-targets --all-features -- -D clippy::correctness -D clippy::suspicious
cargo test --locked --manifest-path src-tauri/Cargo.toml
npm run check:versions
npm run build
npm run typecheck
npx vitest run                              # vitest carries vite-plugin-solid; DOM tests opt in per file with `// @vitest-environment jsdom`

# Cross-engine driver conformance (after touching driver.rs / a driver):
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib driver_conformance  # embedded (DuckDB+SQLite)
scripts/conformance.sh                                # + Postgres, MySQL & SQL Server via throwaway Docker containers
```

Actions and Docker images are pinned; validation permissions are read-only. `npm audit --audit-level=high`, `npm run check:licenses`, and `cargo deny --manifest-path src-tauri/Cargo.toml check advisories licenses sources` are CI dependency gates.
- Installers are built only by `.github/workflows/release.yml` from a `v*` tag (or manual dispatch naming an existing tag). The verify job requires the tag commit on the default branch and exact version parity across `package.json`, `Cargo.toml`, `tauri.conf.json` and `packaging/arch/PKGBUILD` (`scripts/check-version.mjs`); build jobs use the protected `release` environment, fail without `TAURI_SIGNING_PRIVATE_KEY`, and alone receive `contents: write`. macOS arm64/x64, Windows and Linux x64 + arm64 builds draft the release. **The Linux job (`build-linux`, a two-row matrix on `ubuntu-24.04` / `ubuntu-24.04-arm`) runs in a digest-pinned `ubuntu:22.04` container**: GitHub is retiring the `ubuntu-22.04` runner image (brownouts from 2026-09-17), but 22.04 stays the BASE because a Tauri binary links the host's glibc and WebKitGTK, so the build host sets the floor — glibc 2.35 + webkit2gtk 4.1 runs on Ubuntu 22.04+/Debian 12+/Fedora 36+/Arch/Bazzite, whereas a 24.04 build would refuse anything below glibc 2.39. `NO_STRIP=true` keeps the binary's symbol table (crash reports symbolize their backtraces; Windows/macOS ship unstripped too) and sidesteps linuxdeploy's bundled-strip failures. One Linux build yields `.AppImage` + `.deb` + `.rpm`, each with a minisign `.sig`; tauri-action writes `linux-x86_64` (AppImage) plus `linux-x86_64-appimage/-deb/-rpm` keys into `latest.json`, and `tauri-plugin-updater` ≥ 2.10 replaces an AppImage in place or installs a `.deb`/`.rpm` through pkexec/sudo (so on an immutable distro only the AppImage can self-update). Don't cross-compile locally.
- **Built-in updater:** `tauri-plugin-updater` polls `releases/latest/download/latest.json` (published releases only — a draft is invisible to it). The `.app.tar.gz` assets on a release are the macOS updater payload (the DMG is only the human installer) and every `.sig` is the minisign signature the updater verifies — `latest.json` embeds the same signature text, so the standalone `.sig` files are redundant but harmless. ## Conventions

- Update `CHANGELOG.md` (`[Unreleased]`) on every change. **Entries are user-facing release notes**, not commit summaries: each release section is published verbatim as the GitHub release body (`scripts/release-notes.mjs` in the verify job — an empty/missing section FAILS the release) and rendered in-app by the post-update What's-new popup (`src/WhatsNew.tsx` + `src/releaseNotes.ts`, CHANGELOG bundled via vite `?raw`). Write what changed and why, `- **Lead sentence.** detail` bullets under `### Added/Changed/Fixed`, section head `## [x.y.z] - date`.
- Run the applicable validation commands above after edits; Rust/driver changes require the Rust and conformance gates, frontend changes require build/type/tests, and version changes require `npm run check:versions`.
- **The manual ships with the feature.** Any user-facing change also updates the affected `src/help/content.ts` facts in the same change (targeted edits are fine — full regeneration is only for wholesale rewrites), and each release adds a digest section to the `whats-new` topic. Stale help is a bug: the 0.9.x releases shipped with six factual errors in the manual because this wasn't enforced.
- Surfacing errors: `db.rs`'s `From<tokio_postgres::Error>` unwraps the real Postgres message (don't regress to bare "db error").
- Caveman chat style seen in history is a *session* preference (the `/caveman` skill), **not** a code/docs convention — write code, commits, and docs normally.

## Architecture

### Backend — `src-tauri/src/`
- **`lib.rs`** — Tauri command layer and connection registry (`HashMap<id, Arc<Conn>>`; each `Conn` has a closed flag + `AsyncMutex<ConnState>`). Several connections are open at once: `register` is capped at `MAX_OPEN_CONNECTIONS` (16, re-checked under the registry lock so two racing connects cannot both land) and `connect`/`connect_profile` pre-flight the cap before dialling. `active_conn_id` is set by the frontend's `set_active_connection` on every switch and is only a DEFAULT for work not already pinned to an id; `disconnect` touches nothing but its own entry, and stops a Slack bot bound to the closing connection. `run_query` enforces one owner tab, asks `query_plan::plan` for the whole pre-execution verdict (checked engine-aware `script::parse_for_engine`, the complete manual-transaction lifecycle preflight, the read-only verdict, the execution path), then `exec_plan` closes only the old result stream, applies per-tab search path for work statements, and streams only a single cursorable statement. A failed command settles its transaction consequence through `ConnState::settle_failure` (`query_plan::failure_kind`: server-unwound / lost / recovery-required / plain), the same call `fetch_more` and the conformance harness use. Ordinary idle multi-statements with no transaction control use one app-owned atomic script wrapper and return a summary; explicit-control and already-owned scripts run statement-by-statement on the manual session. It never replays a command after the server may have seen it. `transaction_status` exposes authoritative state; disconnect best-effort rolls back an owned session. `cancel_operation` targets the armed query/fetch/export/import through generation-scoped cancel entries outside the connection mutex; PostgreSQL cancel waits for owner unwind before the next arm. Result/IPC/SQL/file/history payloads are bounded. `validate_sql` remains PREPARE-only and never executes. Export accepts one read-only result query or validated inline rows. History/text writes and migration use durable atomic replacement. `backup_to_file`/`restore_from_file`/`read_backup_header` require idle sessions (restore additionally refuses read-only connections) and arm a generation-scoped cancel entry whose optional cooperative `soft` flag `cancel_operation` sets — that is how backup/restore stop on drivers with no out-of-band query cancel. Crash, AI, skills, Slack, relationship, permission, import, and file commands are registered here; sidebar DDL still reuses `run_query`. All imports are file imports and live in `import.rs`.
- **`driver.rs`** — `Backend::{Pg,Duck,Sqlite,MySql,MsSql}` owns execution, paging, reconnect, cancellation handles, the driver-level read-only belt (it calls `sqlguard`, never up into `lib.rs`), transaction capabilities/state, database naming, boolean typing, and introspection. `PgConn`/`MySqlConn`/`MsSqlConn` each additionally own an optional `ssh::Tunnel`: `connect`/`reopen` call `ssh::ensure` then dial `ssh::dial_config`, while `config()` keeps returning the user's real destination (so Slack isolation, display, and cancel TLS are unaffected). Single reads stream with a PostgreSQL cursor or bounded LIMIT/OFFSET pages; ordinary scripts run through one transaction wrapper (MySQL DDL still auto-commits). Manual transactions keep the engine session open across calls; MySQL checks out and probes one pinned connection for explicit, configured-next-transaction, and autocommit-off modes. All drivers incrementally enforce text-result budgets. Binary values normalize to lowercase `\x...` hex; invalid text encoding errors. PostgreSQL cancel is out-of-band; DuckDB uses `InterruptHandle` except on Windows, where interrupt is disabled because it poisons the bundled connection; SQLite/MySQL expose no UI-query cancel handle. `CancelHandle::Flag` is a cooperative flag armed by batched operations (bulk import) so cancel works on every engine; multi-table export arms the equivalent `soft` flag alongside the engine handle. `Capabilities.bulk_copy` says only whether the engine has a server-side COPY protocol — file import works on all four and is NOT gated on it. DuckDB remains pinned to `~1.4`, parse-gates user/composed SQL, quarantines poison, installs/loads ICU best-effort, and releases idle file locks only when no manual transaction owns them. SQLite uses `sqlite_master`/PRAGMA; MySQL applies session read-only setup on every pooled connection and keeps the duplicate-column pager fallback. `table_detail` is per-engine and complete on all four: PG `pg_catalog`, MySQL `information_schema` (`statistics` / `KEY_COLUMN_USAGE` / `CHECK_CONSTRAINTS` / `column_type` — NOT `data_type`, which loses the length a `MODIFY COLUMN` must restate — plus table/column comments and triggers), SQLite `PRAGMA table_info|index_list|index_info|foreign_key_list` + `sqlite_master`, DuckDB `duckdb_indexes()`/`duckdb_constraints()`/`duckdb_columns()`/`duckdb_tables()` best-effort (the last two supply the table and column comments `ddlCaps` lets you write; a view's own comment is still `None`). **Constraint `def`s are shaped as the CLAUSE a `CREATE TABLE` can take back verbatim** (`UNIQUE ("a")`, `FOREIGN KEY (…) REFERENCES …`), because the SQLite table rebuild pastes them straight back in. SQL Server (`tiberius-ng`, one TDS session behind an async mutex) pages by appending `OFFSET … ROWS FETCH NEXT … ROWS ONLY`, verifies `@@TRANCOUNT`/`XACT_STATE()` after every manual-transaction statement, reads row counts from a follow-up `@@ROWCOUNT` batch, and introspects `sys.*`; it has no session read-only flag and no cancel handle.
- **`db.rs`** — `ConnectionConfig` (including the optional `ssh` block), `AppError` (rich error surfacing, plus the boxed `ssh_host_key` prompt payload), `SshHostKeyPrompt`, `open()` (TLS/sslmode/read-only), `make_tls`/`ssl_mode_of`, and bounded text-protocol collection. `collect_rows_limited` preserves zero-row column headers, rejects multiple result sets, ragged rows, invalid UTF-8, and oversized pages incrementally (`USER_TEXT_LIMITS`: 50k rows / 10k cols / 2m cells / 1 MiB cell / 64 MiB total; catalog/DDL variants differ). Values crossing IPC remain text-or-NULL; PostgreSQL `bytea`, DuckDB/SQLite BLOB, and MySQL binary values use reversible lowercase `\x...` hex. `pg_string_literal` makes backslash handling independent of session settings and rejects NUL. `ident` is shared with the import/DDL paths; `CURSOR_NAME` names the one UI cursor.
- **`profiles.rs`** — saved connections. Metadata → bounded, atomically replaced `<app-config>/connections.json`; password → OS keychain (`keyring`), never plaintext or frontend-visible. `Profile.environment: Option<String>` (`dev`/`staging`/`prod`, `#[serde(default)]`, absent = untagged) is cosmetic metadata: it never reaches `ConnectionConfig` and is deliberately outside `same_destination`, so retagging never forces password re-entry. `src/environment.ts` parses it (unknown → `none`) and drives the prod rail/badge on the chip, tab, status bar and confirm-dialog titles. Updating driver/host/port/user/database/path **or the SSH endpoint** while retaining password is forbidden: user must re-enter it, and metadata/keychain changes use rollback plus a credential-free handoff so a crash cannot bind a new secret to the old destination. The SSH password / key passphrase is a second `CredentialPlan` under the `<id>:ssh` account with the same rules (`check_id` restricts ids to `[A-Za-z0-9._-]` so an id can never impersonate that suffix); both plans go through one apply/handoff/rollback sequence, and delete removes both. Delete/restore keychain failures surface.
- **`sqlguard.rs`** — engine-aware statement classification, the ONE home of `mask_sql`, `find_mutation_word_for`, `first_sql_word`, `is_read_only_stmt`, `transaction_requests_write`, `is_cursorable`, `is_wrappable_read` and `wrap_capped`. The command layer, the driver, export and the Slack gate all call down into it; it calls only `script`. It used to be split between `lib.rs` and `slack/processor.rs` with `driver.rs` calling up through both, and the masker carried its own copy of `script::dollar_tag_end` (now `pub(crate)`). On MySQL an executable `/*! … */` comment fails the read-only verdict outright (the masker keeps only a marker for it). **`query_plan.rs`** — pure execution planning for `run_query`: `plan(sql, engine, status, read_only) -> Option<QueryPlan>` (parse → preflight → read-only verdict once → `Path::Single{cursorable} | AtomicScript | Sequence` + the search-path decision) and `failure_kind(...)`, the post-error transaction classifier whose flag getters are closures because their evaluation order is part of the contract. `driver_conformance::command_exec` plans and settles through the same functions the command does, so a routing rule cannot be tested against a fork. **`script.rs`** — SQL parser/runner. `parse_for_engine()` is the checked execution lexer (`split()` remains lenient for editor classification): comments, engine-specific strings/identifiers/comments, dollar bodies, and top-level `COPY … FROM stdin` + `\.` data. T-SQL adds `[bracket]` identifiers, nested block comments, no dollar quoting, statement-block nesting (`BEGIN`/`END`, `BEGIN TRY`/`CATCH`, `CASE` — but NOT `BEGIN TRAN[SACTION]`) so a `;` inside a procedure body is not a boundary, SQLite reuses that same block counter for `CREATE [OR REPLACE] [TEMP] TRIGGER … BEGIN … END` bodies (`sqlite_trigger_head` gates it; `CASE … END` counted) so a replayed trigger's own `;` is not a boundary and its closing `END` never reaches `transaction_action` as a COMMIT — the rebuild path depends on this, and a line-only `GO` boundary that is never sent (a trailing `--` or `/* */` comment still counts; a repeat count is refused). `transaction_action_for(sql, engine)` recognizes raw `BEGIN`/`START TRANSACTION`, `COMMIT`/`END`, `ROLLBACK`/`ABORT`, savepoint/rollback-to/release, unscoped `SET TRANSACTION`, and MySQL session autocommit forms; the SQL Server branch instead reads `BEGIN TRAN[SACTION]`, `SAVE TRAN[SACTION] name`, and `ROLLBACK TRAN[SACTION] name` (rollback-to), treats a bare `BEGIN`/`END` as a statement block, and rejects `RELEASE SAVEPOINT` / `SET TRANSACTION` / `SET IMPLICIT_TRANSACTIONS` with an explanation. `mssql_paging()` classifies which T-SQL windowing form can page one read. `preflight_transactions` validates the whole lifecycle before execution: no nested/prepared/chained units, failed-state work, unsupported engine features, hidden MySQL executable controls, or implicit-commit statements inside an owned MySQL transaction. Ordinary idle scripts remain app-owned and atomic; explicit-control scripts are not nested in that wrapper. PostgreSQL inline COPY participates in whichever transaction owns the script. `effective_start_for(sql, engine)` skips leading comments with the engine's rules (T-SQL nests them) and backs `first_word_for`/`contains_code_word_for`/`statement_words_for`, so every guard classifies the statement the server will run; `effective_start()` is the PostgreSQL-defaulted shorthand. `parse_stream_chunk` is the streaming form of the SAME lexer (`split_core`): it returns the complete items, their start offsets, and the byte offset where the incomplete tail begins — restore feeds a dump through it instead of forking a second splitter.
- **`ssh.rs`** — SSH tunnelling for the network drivers (`russh`, pure Rust, no OpenSSL/libssh2). `SshConfig` (host/port/user/auth/key_path + two secret fields that deserialize but never serialize) is validated per auth method and rejected for embedded drivers. `Tunnel::open` runs the whole bring-up under the 10s connect timeout and names the failing stage; auth is password, private key (OpenSSH/PEM + optional passphrase), or ssh-agent (`$SSH_AUTH_SOCK` on Unix, `\\.\pipe\openssh-ssh-agent` on Windows). A tunnel binds `127.0.0.1:0` and opens one `direct-tcpip` channel per accepted connection, pumped with `copy_bidirectional`; the session and accept loop are owned by the `Tunnel`, so drop closes both. `ensure()` reuses a live tunnel, rebuilds a dead one on a **fresh** port, and drops it when the config stops tunnelling; `dial_config()` produces the loopback config the driver actually dials (`ssh: None`, so setup can't nest). Host keys resolve to `Trusted`/`Unknown`/`Changed`/`Revoked` against `~/.ssh/known_hosts` and the bounded, atomically written `<app-config>/ssh_known_hosts.json`. **known_hosts is parsed HERE, not by `russh`** (`scan_known_hosts` over `ssh_key::known_hosts::Entry`): russh's parser splits each line on one space, reads field 3 as the key blob, and `?`s the whole file on a line it cannot decode — and mapping that `Err` to `Unknown` silently downgraded a CHANGED key (no bypass) to an unknown one WITH a Trust button. Tusk's parser is whitespace-tolerant and understands `@revoked`/`@cert-authority` markers, comma lists, `!` negation, `*`/`?` globs (case-folding), `[host]:port` and hashed `|1|salt|hash` names (HMAC-SHA1 via the `hmac`/`sha1` deps). Unrelated malformed lines are skipped as OpenSSH skips them; an unreadable/over-sized file, a corrupt trust store, or an undecodable record for THIS host is an `Err` the handler REFUSES on — never a trust prompt. `Unknown` returns the structured fingerprint prompt, `Changed`/`Revoked` are refused with no bypass, and `trust_host` records an accepted key (one fingerprint per host; a rotation replaces it). `set_trust_dir` publishes the config dir at startup. `tls_host()` supplies the certificate name for a tunnelled connection so `verify-full` checks the configured host rather than `127.0.0.1` (PostgreSQL: `db::open_with_tls_host` → tokio-postgres `host`+`hostaddr`; MySQL: `SslOpts::with_danger_tls_hostname_override`). `Drop` aborts the accept loop AND every in-flight forwarder (capped at 64).
- **`export.rs`** — options-driven CSV/TSV/JSON/SQL/Markdown/xlsx export shared by full-query, loaded-row, clipboard-parity, and Slack paths. Every sink validates options, columns, projections, row shape, duplicate JSON names, 1 MiB values, and metadata/output budgets. File paths use sibling temp files, sync, and atomic replacement; failure/cancel leaves the previous destination untouched, while zero rows still produce a valid configured artifact. SQL output is source-dialect aware (PostgreSQL/DuckDB/SQLite/MySQL/SQL Server identifiers and safe literals, including T-SQL `bit` columns and 1/0 boolean literals) and batches multi-row INSERTs by tuple count plus bytes. PostgreSQL uses a snapshot cursor; other drivers page through the same feeder. xlsx uses constant-memory worksheet tempfiles and rolls at 1,048,576 rows. `SqlOptions.create_sql` (reconstructed engine DDL from `object_ddl`) replaces the synthetic all-`text` CREATE when present. `export_tables` writes one configured file per table into a directory, emitting `export-tables-progress`, continuing past a failed table (reported by name, files already written untouched) and stopping only on the cooperative cancel flag it arms alongside the engine handle. The xlsx sheet-name character rule is enforced for the xlsx format only — it is inert metadata for the others, like `sql.table`. Boolean export parity remains `export.rs` ↔ `src/formats.ts` ↔ `src/grid/bool.ts`. `SqlDialect` plus `ident_for`/`value_for` are public so `backup.rs` reuses the dialect quoting/literal rules rather than duplicating them.
- **`backup.rs`** — native backup/restore; no external binaries. `run_backup` walks `build_tree`, topologically orders tables from `schema_relationships`, and writes ONE plain-SQL dump: header comment, optional transaction opener (`begin_stmt` — `BEGIN TRANSACTION` on SQL Server, where bare `BEGIN` opens a statement block, `BEGIN` elsewhere), optional drops (reverse order), schemas, sequences, tables, **data**, views, functions/triggers, deferred foreign keys, then PostgreSQL `setval`s. **FK deferral is PG/MySQL/SQL Server** (`deferrable_fks`) — they are lifted out of `ddl.rs`/`sys.*` output and out of MySQL `SHOW CREATE TABLE` into trailing ALTERs so FK cycles restore; SQLite/DuckDB have no `ALTER TABLE … ADD CONSTRAINT`, so theirs stay inline (SQLite emits `PRAGMA foreign_keys = OFF` before any BEGIN, and `topo_order` reports a cycle it could not order so the dump records a warning). **Functions and triggers are PostgreSQL-only** too; other engines get an explicit `-- warning:` naming what the dump does not carry. PostgreSQL sequences are scoped to the dumped schemas, a `tables` scope carries the sequences its tables own (`pg_depend` deptype `'a'`/`'i'`, so a `serial` DEFAULT resolves), and each `setval` read runs inside a SAVEPOINT so one unreadable sequence is a warning, not an aborted transaction. PostgreSQL data streams `COPY … TO STDOUT` into `COPY … FROM stdin` blocks (reopened every 16 MiB so restore's per-unit cap holds) inside one repeatable-read read-only transaction; other engines page into batched multi-row INSERTs through `export::ident_for`/`value_for` (never a forked literal path), with declared-binary columns emitted as native blob literals. Output uses sibling temp + fsync + atomic rename. `run_restore` streams the file through `script::parse_stream_chunk`, executes item by item via `run_single`/`run_manual_copy`, skips comment-only statements, strips a leading BOM, reports the first failure with statement index and line, and never replays after a drop. It brackets the run with `Backend::begin_bulk_session`/`end_bulk_session`, which pins ONE MySQL pooled connection so the dump's own `SET FOREIGN_KEY_CHECKS = 0` applies to the statements after it (and cannot leak into a later query). A cancel is reported as `cancelled` even when it surfaced as a statement error, and `committed` is only meaningful alongside `single_transaction`. `read_header` also reports a psql `meta_command` (`\restrict`) so the dialog can warn before anything runs. Limits: 2 GiB file, 256 MiB per statement/COPY block — enforced BEFORE each read (below the EOF branch it was skipped entirely by a block running to end of file), with the read size clamped so the leftover-doubling cannot pass it. Progress is a `&mut dyn FnMut(..) + Send` callback that `lib.rs` turns into `backup-progress` / `restore-progress` events.
- **`import.rs`** — file-driven import. `import_preview(path, options)` parses the head of a file with no database involved (columns, first 50 rows, warnings, xlsx sheet names); `import_from_file` streams the same file from disk in bounded batches, so file bytes never cross IPC. A blocking parser task feeds the async loader over a bounded channel; the row load is one transaction (clear → load → commit), cancelled cooperatively through `CancelHandle::Flag` armed on the generation-scoped `cancel_operation` path. PostgreSQL streams a conflict-free load through `COPY … FROM STDIN` (`copy_line`, same validation and row-numbered errors as `literal`); every other engine/mode batches multi-row INSERTs. **MySQL DDL implicitly commits AND ends the transaction**, so a `create` import runs its `CREATE TABLE` before `begin()` and reports it via `ImportSummary.created_outside_transaction` plus a note on the failure — never inside the unit, where every later INSERT would autocommit and ROLLBACK would be a no-op. Delimited acceptance is defined here, not shared with `src/formats.ts` (quotes only open a field — or quoting is off entirely when `quoteChar` is empty; characters after a closing quote and unterminated quotes error; blank lines are separators; short rows pad with NULL; wide rows and duplicate/empty/over-long headers reject; UTF-8 BOM stripped). JSON accepts an array of objects or NDJSON, rejects duplicate keys, bounds each element before reading it, and keeps discovering keys during the run so a swapped file is refused and a late key warns. xlsx reads through `calamine`, checking declared dimensions before materializing where the format allows. Values are coerced by the mapped column's declared token (`text`/`integer`/`bigint`/`numeric`/`boolean`/`date`/`timestamp`) into engine-correct literals, so a bad value fails the whole import with a row number. Blank means whitespace-only too; dates/timestamps are calendar-validated and trimmed (MySQL drops a trailing `Z` and refuses a numeric offset). Conflict handling is per engine: PostgreSQL `ON CONFLICT DO NOTHING`/`DO UPDATE`, MySQL `INSERT IGNORE`/`ON DUPLICATE KEY UPDATE`, SQLite/DuckDB `INSERT OR IGNORE`/`OR REPLACE`. **SQL Server is refused** with an explanation; App's `importGate()` disables the Explorer's import items for that reason (not the DDL one). `ColumnType::sql` is a PARITY PAIR with `SQL_TYPES` in `src/import.ts`.
- **`tree.rs`** — introspection. `build_shallow()` = fast connect-time tree (`DbTree { database, databases, schemas[] }`, each schema's tables/views/sequences/functions as **name+kind stubs** + table comment; includes empty schemas). `RelStub` also carries `rows: Option<i64>` (planner `reltuples::bigint`; `-1`/never-analyzed → `None`) + `size: Option<String>` (`pg_size_pretty(pg_total_relation_size)` for tables/matviews only, via a relkind-guarded CASE); SQL Server fills both from `MSSQL_REL_STATS` (size on tables only — a view has no storage), and the other drivers construct stubs with `None`. `table_detail(schema, name)` = lazy per-relation columns (with `is_pk`/`is_fk`/nullable/default/**comment**/**`identity`**), indexes, constraints, **triggers** (`pg_trigger`/`pg_get_triggerdef`, `NOT tgisinternal` so FK-internal triggers stay hidden) — resolves the relation's OID via a **parameterized** query, then drives detail queries by that trusted integer. `Column.identity` is a PG identity-or-`nextval` default (`a.attidentity::text` — a "char", so this cast is correct and is NOT the boolean rule), MySQL `extra` `auto_increment`, a SQLite `AUTOINCREMENT` rowid alias, or a DuckDB `nextval(` default; the Modify diff needs it because MySQL's `MODIFY COLUMN` restates the whole definition. `Column` also carries `collate`/`check`/`generated`/`on_update` — the clauses a restatement or a rebuild would otherwise DROP silently — and `Index`/`Constraint` carry `columns` as DATA (empty = unknown; never re-derive key columns by scanning `def`, which substring-matches unrelated names). `RelationDetail.table_options` is SQLite's `WITHOUT ROWID`/`STRICT` tail and `definition_read` is false when the stored `CREATE` text could not be parsed, which makes the Modify dialog refuse to rebuild. **Every driver fills indexes and constraints, and every driver that HAS triggers fills triggers** — DuckDB has none, so `duck_table_detail` returns `triggers: vec![]` by definition, not by omission.
- **`ai.rs`** — AI proxy for `Wire::{Anthropic,Gemini,Openai,Responses}`. Provider id is the OS-keychain account; keys are stored as origin-bound records, legacy raw keys work only at the shipped provider origin, custom keyed origins require explicit approval and HTTPS, and redirects are disabled. Requests validate provider/wire/model/base/messages/roles and enforce 4 MiB input/output, 1 MiB SSE-line, and bounded model/error bodies. SSE parsing handles deltas, provider errors, finish/truncation, final unterminated frames, retry-before-visible-output, and cancellation. Tiny deltas batch at 1 KiB or 30 ms before Tauri IPC. `ai_list_models` uses the same origin-bound credential and keyed Test uses a real completion endpoint, never a public model-list 200.
- **`slack/`** — desktop-hosted Socket Mode bot bound to exactly ONE connection id (`SlackRuntime.connection`), chosen at `start` (default: the workbench's focused connection) and repointable with `slack_set_connection`; `StatusInfo.connectionId` reports it. It never resolves "the active connection" per question — with several open that would let a question change database when the user switches tabs. Autostart is scoped to one SAVED connection: `SlackConfig.bound_profile_id` records it, `config::autostart_target` reads it, launch only calls `slack::arm_autostart` (publishes "waiting for connection <name>", starts nothing), and App starts the bot from `afterConnect` when THAT profile's connection opens. `slack::start(None)` no longer falls back to the active connection and the frontend never binds a running-but-unbound bot, so "whichever connection opens first" cannot happen; an ad-hoc connection has no profile and can be bound by hand but never autostarted. Closing the bound connection stops the bot and publishes ONE status carrying the reason but leaves `slack.json` alone — the old `disarm_autostart` write meant merely opening a dev build disabled a working bot. `StatusInfo.waiting` marks such deliberate stops (`set_waiting`: armed-and-waiting at launch, bound connection closed) so the frontend paints them amber; a stop with an `error` and no `waiting` is a failure and red. Socket envelopes are acked before work, deduped, bounded, and processed sequentially. A question snapshots schema/perms/FKs/skills and optional default-off samples, then AI may propose exactly one wrappable read. Proposal and result ids are 128-bit OS-random capabilities; interactions also bind current allowlists, requester, workspace, channel, thread, exact source message, TTL, connection id, and database. SQL is revalidated at proposal and execution with mutation/lock/output scans, executable-comment rejection, and a conservative deterministic-function allowlist. Approval refuses a changed connection/database and runs on a fresh engine-enforced read-only backend, never the UI cursor; file-backed DuckDB requires no active UI stream and in-memory embedded databases are refused. Results page under live budgets, retain at most 8/64 MiB for 15 minutes, and requester-only export buttons reformat without rerunning. PostgreSQL timeout sends server cancel; MySQL may finish after Tusk stops waiting; embedded calls are synchronous. Config/tokens save transactionally, replacement tokens restart a running bot, and non-token settings apply next question.
- **`skills.rs`** — user-authored AI instruction bundles (`workspace` or server-reported database-name scope). On-disk/export format is one Markdown file with five scalar frontmatter keys under `<app-config>/skills/`; plain Markdown is a valid import. Limits: 256 regular files, 256 KiB each, id 128 bytes, name 200 bytes, description 2 KiB, database 512 bytes. The skills directory and files reject symlinks/reparse points; create is no-clobber, replace is atomic/synced, and Unix files are mode 0600. `safe_id` blocks traversal; scalar newlines cannot forge keys; corrupt `enabled` stays on, unknown scope degrades to workspace, and one unreadable file does not take down `load_all`.
- **`perms.rs`** — Postgres permission model. `collect(client)` → `Permissions` (the role's **effective** privileges via `has_*_privilege`, accounting for membership/`PUBLIC`/ownership): role attrs (superuser/createdb/createrole), per-schema CREATE/USAGE+owner, per-relation SELECT/INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER+owner (one `pg_class` scan), CREATE-on-current-db. `Backend::permissions()` → PG delegates here, others return `Permissions::unrestricted()` (`enforced:false`). Exposed by the `permissions` command; frontend gates sidebar DDL on it. **Bare `has_*_privilege()` bools come back `"t"`/`"f"` over the text protocol — never `::text`-cast them.**
- **`ddl.rs`** — `object_ddl(kind, schema, name)` reconstructs runnable `CREATE` DDL from `pg_catalog` (pg_dump-style): tables (identity/generated/serial defaults; PK/unique/check inline; **FKs as trailing ALTERs**; plain indexes only — constraint-backed skipped; table+column comments), views/matviews (`pg_get_viewdef`), functions (`pg_get_functiondef`, overloads; aggregates/window flagged via `prokind`), sequences (`pg_sequences`). User input bound as params, then by OID. Out of scope: partitions, inheritance, RLS, triggers, storage params, tablespaces, collations.
- **`main.rs`** — `tusk_lib::run()`.

### Frontend — `src/`
- **`App.tsx`** — workbench shell holding a LIST of open connections. - **`sql/ddl.ts`** — pure SQL builders (the heart of "build SQL in TS"), **dialect-aware via `ddlCaps()`** for all four engines. PG: comma-joined multi-action ALTERs, identity, `USING`, `SET SCHEMA`, index method + partial WHERE, `LIKE … INCLUDING ALL`, `COMMENT ON`. DuckDB: one `ALTER` action per statement, `ADD COLUMN` constraints split into follow-up `ALTER`s with NO backfill (DuckDB rejects `SET NOT NULL` with an outstanding UPDATE in the same transaction, and the run path is transactional — so NOT NULL adds work on empty tables only), CTAS duplicate, sequence-backed auto-numbering, no constraint ALTERs. The rebuild carries the column `COLLATE`/`CHECK`/generated clauses, the table-level constraint clauses (names included) and `WITHOUT ROWID`/`STRICT` across, skips generated columns in the copy, and wraps the drop+rename in `PRAGMA legacy_alter_table=1/0` (since 3.25 a plain `RENAME TO` re-parses `sqlite_schema`, so a dependent view or trigger aborts the whole edit). Foreign keys are the one thing the script CANNOT handle itself: the intermediate `DROP` performs an implicit `DELETE FROM` that orphans a child row, `PRAGMA foreign_keys` is a silent no-op inside the transaction the script runs in, `defer_foreign_keys` only moves the failure to the COMMIT, and retiring the original by rename does not help because SQLite rewrites other tables' `REFERENCES` to follow a rename even under `legacy_alter_table`. So `App.runDDL` brackets a rebuild — recognised by `isSqliteRebuild(sql)` — with `PRAGMA foreign_keys=OFF/ON` as separate IDLE `run_query` calls, restores it in a `finally`, and the Modify-table note says so. What it CANNOT do safely it refuses in `tableDiffProblems`: a rename in the same pass (the replayed index/constraint/trigger text still names the old identifiers), a drop of a column a surviving object references, an unreadable stored definition, and any rewrite of a generated column (MySQL too). `validateColumns` (empty / duplicate-case-folded / nullable-PK — it reads BOTH `primaryKey` and the Modify dialog's `isPk`, and skips the nullable-PK error where `caps.nullablePrimaryKey`, i.e. SQLite) and `scriptNote` (one transaction vs MySQL's per-statement commit) back the dialogs' validation and note. `mysqlTextLiteral` doubles backslashes only when the session does NOT run `NO_BACKSLASH_ESCAPES` (the backend reads `@@session.sql_mode` at connect and reports it as `Capabilities.no_backslash_escapes`; App pushes it in with `setMysqlNoBackslashEscapes`). MySQL's `ENGINE=`/`CHARSET=`/`COLLATE=` are bare grammar tokens: anything not matching `^[A-Za-z0-9_]+$` is dropped by the builder and reported by `validateTableOptions`. Covered by `sql/ddl.test.ts` (builder output) + `driver_conformance.rs` `{duckdb,sqlite,postgres,mysql}_ddl_builder_forms_apply` and `{duckdb,sqlite}_ddl_*_runs_transactionally`, whose fixtures are SAMPLED from the vitest expectations — the SQLite rebuild scripts are byte-identical on both sides, while the surrounding setup/teardown steps and a few engine-only forms (the PG `SET SCHEMA` pair, MySQL `ADD PRIMARY KEY` / `CREATE TABLE … LIKE`) exist only on the Rust side. - **SQL Server grid sort/filter lifts the ORDER BY out.** T-SQL rejects a bare `ORDER BY` inside the derived table the wrap needs, so `wrapQuery` (`src/grid/query.ts`) splits a TRAILING TOP-LEVEL `ORDER BY` off the base query (`mssqlOrderTail`) and re-applies it after the wrapper's own `WHERE`; a grid sort replaces it. `mssqlWrappable` therefore refuses only what cannot be hoisted: a `WITH`-led statement, ordering inside `OVER (…)` or a subquery, and an `ORDER BY` carrying `OFFSET`/`FETCH` (that pagination has to stay inside — filtering before it would change the page). Incomplete streams and filters still use server wrappers. - **Connection/persistence and revision safety.** Ad-hoc connection keys are JSON tuples captured before connect awaits. Legacy tab/history migration writes and verifies the collision-proof destination before deleting old storage. History revisioning merges early appends with an in-flight load and prevents stale disk state from resurrecting a deliberate clear.

## Gotchas (read before debugging)

- **Values are text, but binary is explicit.** IPC cells are string-or-NULL. PostgreSQL `bytea`, DuckDB/SQLite BLOB, and metadata-confirmed MySQL binary columns render as reversible lowercase `\x...` hex. Invalid server-encoding text is an error, never a replacement placeholder, because the original bytes are unavailable. Use `try_get`, never `get`, on tokio-postgres rows; typed catalog readers must degrade/skip on NULL/type mismatch. Every collection path must use the correct incremental `TextLimits`.
- **Crash/skill file boundaries.** Rust panic hook → bounded `<app-config>/last-crash.txt`; frontend `CrashGuard` bounds reports to 96,000 bytes and contains render/window errors. Crash files max at 128 KiB, require regular UTF-8 files, reject symlinks/reparse points, use atomic synced replacement, and are mode 0600 on Unix. Consent remains `tusk.crashConsent`; off clears retained reports and nothing auto-transmits. Skills similarly cap at 256 regular files × 256 KiB with bounded scalar fields and safe ids. Perf guards: editor live analysis stops at 1m chars, grid copy caps at 1m cells/8,388,608 chars, ERD at 600 tables/4,000 edges, plans at 2,000 nodes/depth 256, and Slack chart/event handling remains panic-contained with finite values only.
- **DuckDB parser errors poison the connection — never let user SQL hit it unparsed.** The bundled libduckdb (duckdb-rs #209, seen on Windows) leaves an internal mutex locked after a PARSER error (binder/catalog/runtime errors are fine): every later statement fails with "resource deadlock would occur" and **dropping the poisoned connection aborts the process** ("Rust cannot catch foreign exceptions"). `DuckConn::parse_check` prepares each user statement on a scratch in-memory connection (`gate` field) first — a failure that poisons the scratch (probe `SELECT 1` fails) is the parse-error class → report it + `mem::forget` the scratch; a failure that doesn't is a binder error from the empty scratch DB → pass through so the real catalog errors properly. Gated: `run_single` (user text AND the CAST-wrap — a trailing `--` comment can swallow the wrap's `)`), `run_script` per statement, `bool_columns` (the COMPOSED `DESCRIBE {sql}` — `SHOW TABLES`/`SET`/`EXPLAIN` parse alone but are parser errors under DESCRIBE). `fetch_page` is ungated on purpose (its `stream_sql` already passed the gate). Single-statement prepare never executes (duckdb-rs auto-executes only the LEADING statements of a multi-statement string) — keep the gate one-statement-at-a-time. **Poison classes the gate can't stop** (`interrupt()`, unforeseen paths) are handled by `quarantine_poisoned`/`quarantine_if_poisoned` — probe `SELECT 1` after an error, take+`mem::forget` a poisoned connection (drop aborts; the leaked handle keeps a file-backed DB locked until app restart) and tell the user to reconnect; `release_idle`/`Drop for DuckConn` route through `forget_if_poisoned` as the last belt. **DuckDB Cancel is disabled on Windows** (`CancelHandle::Duck` returns an error there — interrupt() = certain poison; a query that can't be cancelled beats a database file locked until restart). **Deadlock trap:** the quarantine helpers re-lock `conn` — never call them while a `d.lock()` guard temporary is alive (bind the operation result to a `let` first; two arms in driver.rs carry the comment). Pinned by `duck_syntax_error_survivable` + conformance `syntax_error_recovery_battery` + `duck_from_first_and_pivot_stream` (FROM-first/PIVOT are cursorable on DuckDB — buffering them whole was an OOM-abort class).
- **Single statement vs script.** One cursorable read statement may stream, including on an owned manual session. Cursorability is decided by `is_cursorable` in `lib.rs`; the bounded structural `script::with_shape` parser identifies the statement CTEs feed, modifying CTE bodies, and `SELECT … INTO`, including engine-specific quoting/comments and PostgreSQL `SEARCH`/`CYCLE` / DuckDB `USING KEY`. `src/plan/explainSql.ts` mirrors that parser for Explain Analyze confirmation and grid wrapping; Explain refuses more than one statement so trailing SQL cannot escape its prefix. The `runStatement` editor action must always prefer an exact non-blank selection over statement-at-cursor resolution — expanding an inner CTE selection can execute an enclosing write. An ordinary idle multi-statement input with no control uses one app-owned transaction and returns only a summary; its trailing read is not split out, so failure still rolls back prior DML (subject to MySQL DDL/nontransactional-table semantics). Raw transaction-control scripts are lifecycle-preflighted and execute on the owner session instead: they may be self-contained (`BEGIN; …; COMMIT`) or span runs. Multi-statement results keep `baseQuery=""`, so grid wrapping/editing stays disabled. Execution uses checked engine-aware `script::parse_for_engine`; editor classification may use lenient `split`.
- **Manual transaction ownership and recovery.** `TransactionStatus {state,revision,id,owner,mode,health}` is authoritative; non-owner queries/fetch/cancel and all `require_idle` metadata/import/query-export/Slack paths fail closed while it owns the session. Supported controls: `BEGIN`/`START`, `COMMIT`/`END`, `ROLLBACK`/`ABORT`; savepoints on PG/SQLite/MySQL/SQL Server (`SAVE TRANSACTION`, no `RELEASE`); `SET TRANSACTION` on PG (active, before work) and MySQL (before START); MySQL-only `SET autocommit=0/1` on one pinned connection. DuckDB has neither savepoints nor `SET TRANSACTION`; SQLite has no `SET TRANSACTION`. PostgreSQL statement/cancel errors require rollback or rollback-to recovery. A dropped/unexpectedly ended session becomes `Lost`: never reopen/replay it; disconnect/reconnect and verify outcome. Healthy close/disconnect/window-close must resolve Commit/Rollback after Apply/discard of owner pending edits; disconnect cleanup still best-effort rolls back the physical session.
- **Transaction result provenance and grid Apply.** Every result/pending edit records transaction id + revision. Pre-BEGIN rows must rerun before editing; commit, rollback, rollback-to, autocommit-unit boundaries, and loss conservatively stale affected snapshots while leaving them visible. Outside a manual transaction the grid preview **Commit** uses the app-owned atomic script; inside the owner transaction it becomes **Apply**, runs on the outer unit, clears pending changes on success, and does not commit. Transaction-bar Commit/Rollback is separate. History includes scoped control and grid-Apply markers.
- **Backup/restore are whole-connection operations.** Both need `require_idle` and go through the frontend's `interruptStream` first; restore is additionally blocked on read-only connections. A dump is written to a sibling temp file and renamed only on success, so cancel/failure never touches the previous file. Restore executes each statement exactly once — a connection drop mid-restore aborts with a verify-state error, never a replay. Tusk's own dumps reopen `COPY` blocks every 16 MiB precisely so restore's 256 MiB per-statement/per-COPY-block cap always holds; a foreign dump with one enormous COPY block is rejected by that cap, not silently truncated. Cancellation flows through the SAME `cancel_operation` generation entry as query/export, using its cooperative `soft` flag.
- **File imports parse in Rust; `formats.ts` formats, it does not parse.** `import_preview`/`import_from_file` take a path, never a payload. There is exactly ONE import parser (`import.rs`) and its `tests` module is the sole acceptance authority — `formats.ts` lost its duplicate CSV/JSON parsers precisely because they had drifted from it while claiming parity. Clipboard paste parses separately in `grid/paste.ts`. Streaming can't widen a headerless file to its widest row, so the parser fixes the width at the first data row; JSON numbers go through `serde_json`, which canonicalises (`1.50` → `1.5`). The parity pairs that DO remain are `ColumnType::sql` ↔ `SQL_TYPES`, the inference/coercion fixture, and `sanitize_sheet` ↔ `sanitizeSheetName`.
- **SQL Server pages by appending, never by wrapping.** T-SQL has no `LIMIT`, and a derived table may contain neither `WITH` nor a bare `ORDER BY` — so `MsSqlConn::page_sql` appends `OFFSET n ROWS FETCH NEXT m ROWS ONLY` to the user's statement rather than wrapping it. `script::mssql_paging` picks the form: `Append` when a top-level `ORDER BY` already exists (order preserved), `OrderNull` when there is none (adds `ORDER BY (SELECT NULL)`; page order is then engine-defined, exactly like MySQL's LIMIT/OFFSET), and `Buffered` for shapes that cannot take the clause (`TOP`, an existing `OFFSET`/`FETCH`, `FOR XML|JSON`, `OPTION`, or an unordered set operation) — those read once under `USER_TEXT_LIMITS` with an explanatory `note`, never a silently truncated page. The same restriction is why `grid/query.ts` refuses to wrap a `WITH`-led or already-ordered statement for sort/filter there. `bit` renders `true`/`false`, and `grid/bool.ts`'s `isBoolType` matches `bit` **only** under the mssql dialect (PostgreSQL's `bit` is a bit string). What it COMMITS is `boolEditTokens`: `1`/`0` on SQL Server, SQLite and MySQL, `true`/`false` on PG/DuckDB — T-SQL has no `TRUE`/`FALSE` literal and `bit` cannot take the `N'true'` `lit()` would emit. Same split in `grid/filterSql.ts`, `src/formats.ts` and `export.rs`.
- **SQL Server has no session read-only flag and no out-of-band cancel.** The uniform client guard (`is_read_only_stmt`, called with `TransactionEngine::MsSql` so nested comments and brackets are read the way the server reads them) is the whole read-only story there — `readonly_mssql_blocks_writes` pins it — and `SET TRANSACTION ISOLATION LEVEL` is not a substitute (it is session-wide, which is also why preflight refuses it). `CancelHandle::None` means a running query finishes; the UI shows a Running timer rather than a Cancel that cannot work. Row counts come from a follow-up `SELECT @@ROWCOUNT` batch (session state survives the batch boundary) because the TDS query stream discards DONE tokens; a failure there degrades to a bare `OK`, never a wrong number.
- **COPY detection ignores leading comments** (`effective_start`). pg_dump prefixes every COPY with a `--` block; missing this sends COPY to `batch_execute` → `CopyInResponse` → "unexpected message from server".
- **Keychain in dev:** unsigned `tauri dev` builds re-prompt / invalidate saved passwords across rebuilds (macOS ties items to the code signature). Seamless in signed release builds. `keyring` features are per-OS in `Cargo.toml`. **On Linux the keychain is `sync-secret-service`**: it links `libdbus-1` (so `libdbus-1-dev` is a build dependency and the `.deb`/`.rpm` declare `libdbus-1`/`libssl` explicitly under `bundle.linux` — Tauri auto-adds only webkit/gtk) and needs a Secret Service provider (GNOME Keyring, KWallet, KeePassXC) running at runtime, or saving a password errors.
- **Linux desktop quirks live in two places.** `lib.rs` `apply_linux_webkit_workarounds` runs first thing in `run()`, before any thread exists: when the proprietary NVIDIA module is loaded (`/proc/driver/nvidia/version` exists — nouveau does not create it) and the user has not set it, it sets `WEBKIT_DISABLE_DMABUF_RENDERER=1`, the documented fix for WebKitGTK's blank window on NVIDIA (tauri-apps/tauri#9394). It is gated by `cfg!`, not `#[cfg]`, so the Windows/macOS gates still compile it. `tauri.conf.json` `bundle.linux` holds the deb/rpm extra deps and points both at `src-tauri/linux/tusk.desktop`, a Handlebars template (`comment`/`exec`/`icon`/`mime_type` are the variables Tauri supplies) that titles the menu entry *Tusk* with SQL keywords; the AppImage reuses the deb's data tree, so it inherits the entry. The AppImage bundles WebKitGTK's helper processes from the build host — one more reason the Linux build host must be the oldest supported base. The Flatpak manifest grants `--filesystem=home` on purpose: DuckDB/SQLite need sibling WAL/lock files and SSH tunnels read `~/.ssh`, which the portal's per-file grants cannot express; `--talk-name=org.freedesktop.secrets` is the keyring.
- **Connect-on-startup fires in `npm run tauri dev` too — plan smoke tests around it.** A profile with `default_connect` is connected by `App.onMount` on EVERY launch of the dev build, and the user's default may point at production. Before driving the app, know which profile holds the flag and be ready to disconnect immediately. It fires ONCE PER PROCESS: the module-level `startupAutoConnectDone` flag in `App.tsx` plus `connections.ts`'s pure `shouldAutoConnect` mean an HMR update or a "Try to continue" remount re-runs `onMount` without reconnecting (the profile is offered in the reopen list instead) — a real relaunch still connects. For CDP work, the installed release build owns the shared WebView2 user-data dir, so `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` is silently ignored while it runs — launch with a scratch `WEBVIEW2_USER_DATA_FOLDER` to get a private browser process (and a clean localStorage, so tabs/layout/consent start empty).
- **TLS:** `native-tls` (SecureTransport on mac, SChannel on Windows; needs OpenSSL on Linux). `sslmode`: `disable` | `prefer` (default) | `require` (encrypt, no cert verify) | `verify-full` (verify).
- **SSH tunnels dial loopback, but TLS still verifies the configured host.** The driver is pointed at the tunnel's local port, so every tunnelling driver needs an explicit "connect here, verify that name" split, fed by `ssh::tls_host(config, tunnel)` (which returns the untunnelled hostname, or `None` when there is no tunnel): PostgreSQL sets `host(name).hostaddr(addr)` in `db.rs`, MySQL uses `with_danger_tls_hostname_override`, SQL Server uses tiberius' `hostname_in_certificate` (which drives both SNI and the verified name while `cfg.host` stays on the loopback dial endpoint). Miss it on a new driver and `verify-full` fails against `127.0.0.1` with no hint the tunnel caused it. Never widen `make_tls` to paper over that instead.
- **A tunnel's lifetime is the backend's.** `PgConn`/`MySqlConn`/`MsSqlConn` own the `Tunnel`; dropping it aborts the accept loop and closes the SSH session, and a rebuilt tunnel always binds a *new* loopback port. Every reconnect path must go through `ssh::ensure` before `db::open`/`MySqlConn::open`, or a stale port could be dialled after the session died. `MySqlConn::open` takes the tunnel by value for exactly this reason — `reopen`'s `*m = nm` would otherwise drop the live session mid-handover.
- **Host-key trust is tri-state, and only one state is promptable.** `Unknown` carries `AppError.ssh_host_key` (key type + `SHA256:` fingerprint) and the frontend offers Trust; `Changed` never does, and must not grow a bypass. `~/.ssh/known_hosts` is read but never written — Tusk records accepted keys in its own `ssh_known_hosts.json`. `AppError.ssh_host_key` is **boxed**: unboxed it pushes `AppError` past clippy's `result_large_err` threshold and lights up ~150 warnings across the crate.
- **Read-only mode:** engine enforcement where available plus one uniform client guard. **The guard is engine-aware** (`sqlguard::is_read_only_stmt(sql, engine)`; the verdict is applied once by `query_plan` and again as a belt in `driver.rs`): T-SQL nests `/* */` and quotes identifiers with `[brackets]`, so classifying its SQL with PostgreSQL's rules read a different statement than the server executes. Only read forms pass, the mutation scan ALWAYS runs (only MySQL's `SHOW CREATE …` is exempt, and only for that one word — the old blanket `SHOW` short-circuit was a write bypass on SQL Server), and the masked scan rejects writable CTEs, row locks, table/file output, mutation words, and `set_config`; `EXPLAIN ANALYZE` is blocked because it executes its inner statement. Inline COPY/import and sidebar mutations are blocked. Slack adds wrappability, executable-comment, and conservative function-policy gates on top.
- **Dropped connections reconnect, never replay.** `ensure_alive` reopens a closed backend before the next explicit command, but `run_query` never retries after a command may have reached the server, even for read syntax: volatile functions/external effects make outcome ambiguous. The error tells the user to verify state. Connect timeout/keepalives still surface dead PostgreSQL links without capping live query duration. A lost streaming cursor returns an explicit incomplete-result error; fetch errors roll back/reset pager state. Run cancellation is armed for the initial query and each fetch.
- **Autocomplete corrupting dollar-quotes** was caused by Enter-accept **combined with `$` being a completion token** (so `$tag$` delimiters were offered and replaced on accept). The fix that matters is keeping **`$` out of completion tokens** — with that in place, Enter-accept is safe and is now enabled (Enter accepts like Tab; `acceptCompletion` no-ops to a newline when no popup is open). Don't re-add `$` to completion tokens.
- **Lazy tree ⇒ autocomplete uses `list_schema`, not the tree.** The shallow `db_tree` no longer carries columns, so autocomplete is fed by `list_schema` (one query). Expanding a node fetches `table_detail` (cached); after DDL, `runDDL`→`loadSchema` refetches the shallow tree + `list_schema` and re-fetches already-open details.
- **Sidebar DDL must stay single-statement where it matters.** `CREATE/DROP DATABASE` can't run in a transaction — keep them one idle statement (ordinary multi-statement input routes to the app-owned wrapper). Most builders in `sql/ddl.ts` emit one statement each (comma-separated ALTER actions where the engine takes them); the deliberate multi-statement cases are duplicate-with-data, column edit + rename, DuckDB's split ALTERs, `CREATE TABLE` + `COMMENT ON`, and the SQLite rebuild — all table-scoped and safe inside the app-owned transaction (MySQL excepted, where each DDL statement commits itself; `scriptNote` says so in the dialog). Explorer DDL is frozen during manual transactions; raw owner SQL remains engine-authoritative, with recognized MySQL implicit-commit forms blocked inside the tracked unit.
- **Copy DDL is reconstructed, not pg_dump.** Driven by OID; constraint-backed indexes are skipped and FKs deferred to trailing ALTERs so replay doesn't error. Partitions/inheritance/RLS/triggers/storage are out of scope (see `ddl.rs`).
- **Quoting parity + dialect.** `sql/ident.ts` `ident` is **dialect-aware** (`setSqlDialect`): MySQL = backticks `` `x` ``, SQL Server = `[x]` (with `]` doubled), everyone else = double `"x"`; literals are `'…'` for all except SQL Server's `N'…'`. **The module var is the ACTIVE connection's dialect** — an App effect re-applies `setSqlDialect` on every active-connection switch. Several connections are open, so any SQL built for a SPECIFIC tab, dialog or frozen snapshot must pin its own: builders that already take a dialect/kind get the owning connection's (`wrapQuery`/`wrappableQuery`, `buildCommitScript`'s `input.dialect`, `formatWithOptions`/`formatForCopy`, `explainSql`, filter SQL), and everything reaching `ident`/`lit`/`sqlDialect()` implicitly (`sql/ddl.ts` via `ddlCaps()`'s default arg, the Explorer scaffolds, export previews) is wrapped in `withDialect(kind, …)`. `withDialect` is synchronous only — never `await` inside it. It saves and restores the MySQL `NO_BACKSLASH_ESCAPES` flag along with the dialect (that flag lives in `sql/ident.ts` beside `lit`, not in `sql/ddl.ts`, precisely so the borrow is complete), and resets it to the default when the borrowed dialect differs — another connection's `sql_mode` is unknowable. Connection-scoped dialogs/menus close on an active-connection switch, because their live SQL preview renders with the active dialect and their Run is pinned to the origin connection anyway. For **Postgres** it matches Rust `db::ident` — and `db::ident` is only used on PG-only backend paths (import / DDL recon), so the parity that matters is PG↔PG. **Editor dialect follows the connected driver**, not a manual selector: `activeDialect = conn() ? driverDialect(caps().kind) : prefs().dialect` (DuckDB → `postgres` dialect; the old toolbar dialect `<select>` was removed). Always quote identifiers in generated SQL.
- **Never `::text`-cast a boolean in catalog queries.** `collect_rows` reads the text protocol: a *bare* bool comes back `"t"`/`"f"`, but `bool::text` (e.g. `i.indisunique::text`, `(con.oid IS NOT NULL)::text`) comes back `"true"`/`"false"`. The code compares against `"t"`, so a cast silently makes every check false. Select the bare bool (`i.indisunique`, `(NOT a.attnotnull)`). Char columns (`relkind`, `attidentity`, `contype`) DO need `::text`.
- **`editor/lexer.ts` must mirror `script.rs` lexical boundaries — including engine branches.** Auto-fold, lint, formatter carve-outs, current-statement selection, param detection, and safe grid wrapping share it. `lex(doc, engine = sqlDialect())` mirrors `split_impl`'s per-engine rules: MySQL `#` comments and whitespace-required `--`, MySQL backslash escapes inside quotes (consumed leniently where Rust errors on ambiguous `\'`), and MySQL/SQLite backtick identifiers (span kind `btick`; masked by default, kept with `maskNonCode`'s keep flag alongside `dquote` for schema-lint/editability). T-SQL `[bracket]` identifiers (span kind `bracket`, kept alongside `dquote`/`btick` under `maskNonCode`'s keep flag), nested block comments, no dollar quoting, and a line-only `GO` that ends a statement without producing code. SQLite `CREATE TRIGGER … BEGIN … END` bodies share the T-SQL block counter on both sides (`sqliteTriggerHead` ↔ `sqlite_trigger_head`), with identical fixtures in `lexer.test.ts` and `script.rs`. `lexState`'s cache keys on doc AND engine. Execution uses checked Rust `script::parse_for_engine`, while TS/editor classification and Rust `split` remain lenient, so psql meta-commands and malformed inline COPY are rejected only at the execution boundary. Server-lint statement indices can still diverge around COPY data.
- **Auto-fold is display-only.** It replaces ranges with widget decorations; the document text is never modified, so `getRunText`/`getDoc`/export always return the full expanded query. Folds recompute on doc-change (candidate geometry) and on every selection move (cursor in a range → expanded). Don't reach for `@codemirror/language` fold state for this — that's the separate *manual* fold gutter (`foldBasics.ts`).
- **One cursor PER CONNECTION, many tabs.** There's a single server-side cursor per connection, so only one tab *of that connection* can stream at a time — and a run or metadata read on connection A must never disturb connection B's live stream. `interruptStream(reason, connectionId = activeConnectionId())` is therefore scoped: every caller holding a connection passes its id, and the cursor owner, the query/fetch/schema/fk/cursor generations, `running`/`cancelling`/`fetchingMore`/`loadingAll`, and `cancel_operation`'s target all live per connection. Anything that closes a cursor underneath its owner — another tab's run, every metadata command (`db_tree`/`list_schema`/`table_detail`/`object_ddl`/`*_relationships`/`permissions` all `rollback_cursor`), Explorer DDL, all-rows export, import — must go through App's `interruptStream(reason)`, which frees the owner and freezes its snapshot as `ResultSnapshot.incomplete` (toolbar badge, `N rows loaded · reason` status, local sort off, Export "incomplete" label). Operations reach it through the runner's `releaseStream` (the descriptor's `release` reason; `null` for paging, which must not touch the stream); the introspection loaders (`loadSchema`/`loadDetail`/`fetchFkSchema`) still call `interruptStream` directly. Backend belt: `fetch_more` returns `interrupted:true` when the stream owner is still registered but the cursor is gone, and `loadMore` maps that to the same state — never mark a truncated result plainly `done`. Editability's `table_detail` is prefetched in `executeQuery`'s `prepare` phase, after the release and BEFORE the run (and never fetched while the tab streams) because fetching it afterwards truncated every editable result. Best-effort FK-hint fetches skip while a stream is open. `doRun` frees another tab's cursor before running; `cursorOwnerTabId` gates `loadMore` so scrolling a non-owning tab never `FETCH`es the wrong cursor. Idle sidebar commands roll the cursor back; during a manual transaction they are frozen, and an owner run closes only the old stream without rolling back the outer unit. Per-tab editor state (undo/cursor/fold) lives in a `Map<tabId,EditorState>` in `SqlEditor.tsx`; **`view.setState()` replaces all state incl. compartments**, so every tab state is built via the shared `buildExtensions` (seeded with the current dialect/theme/fold), and the guarded value-effect skips during a swap (`props.tabId === curTabId`) so it can't clobber the outgoing tab.
- **The active tab always belongs to the active connection.** That one invariant is what lets every "active X" accessor keep meaning one connection. `switchTab` sets both; `focusConnection(id, tabId?)` sets both and remembers the connection's last tab (`lastTabByConn`). Never call `setActiveTabId`/`setActiveConnectionId` directly outside those two. `activeTab()` falls back to the module-level `NO_TAB` when nothing is open, so memos that run on the connect screen cannot crash; `NO_TAB` is never in `tabs()`, so `patchTab` on it is a no-op. Persistence is per connection key (`recoveryKeys`), and `restoring` guards the debounced save while a connection's tabs are being installed.
- **Grid `<For>` bodies must read via accessors, not `const`.** In `ResultGrid.tsx` the windows iterate index ranges (`range(visCols…)`); inside, use `const oi = () => displayCols()[k]` / `const val = () => rows()[r]?.[oi()]` (functions), NOT `const oi = displayCols()[k]`. A plain const is captured once at item-render; since the `For` key (the index) doesn't change on a sort re-run (rows replaced) or reorder (displayCols changed) with the same window, captured consts go stale and cells show old data / the sort glyph never appears. Read reactively in the JSX. The grid's frozen header/gutter are transform panes (not sticky); a new query bumps `result.epoch` so the grid resets scroll (vs a tab switch, which restores it) — keyed on `${tabId}:${epoch}`. **That key MUST be a `createMemo`, not a plain `() =>` function.** `on()` re-runs its callback whenever a tracked dep *notifies*, not only on value change, and `epoch` reads through App's `activeTab()` memo whose identity changes on every `patchTab`/`patchResult` — so a plain key fired the reset (scrollTop→0 + selection clear) on every row append / resize / reorder / hide, making those feel broken. The memo dedupes by string so the reset runs only on a real tab switch or epoch bump. **Scroll never writes to reactive state**: `onScroll` updates only the local `scrollTop`/`scrollLeft` signals (only the window memos depend on them) + a non-reactive per-tab `scrollMem` Map. Persisting scroll into `gridView`/`setView` per frame rebuilds the tabs array and cascades a full-App recompute every frame — it froze/crashed large tables. Keep scroll out of `view`.
- **Active schema is per-tab, applied per run.** `Tab.searchSchema` (null = default) drives `SET search_path` on the *shared* session — so it must be re-applied (or `RESET`) on every run_query/validate/export, never assumed sticky. Autocomplete labels a table bare when its schema is `public` or the active schema (`makeSqlCompletion`'s 3rd `getActiveSchema` arg). Export scope=all uses the *producing* tab's schema via the `exportSrc` snapshot. Bare-name ambiguity (same table in two schemas) resolves active-schema-first, then `public`, in ONE place — `tableByRef(idx, ref, activeSchema)` in `sql/aliases.ts` — shared by completion AND schema-lint, so the linter can never flag a table completion just offered. **Generated query scaffolds** (`genSelect`/`genInsert`/`genUpdate`, `runTable`) use `qualifyIn(schema, name, activeSchema)` — drops the schema prefix when it matches the tab's active schema — and open a **new tab** via `openGeneratedTab` (schema set to the relation's) rather than clobbering the active tab. DDL builders keep using `qualify` (always explicit — never depend on search_path for drop/alter/rename).
- **A token added to `:root` must be added to every theme block.** The eight palettes are independent blocks, not overrides of a base: a role defined only on bare `:root` silently gives Catppuccin/Dracula/Tokyo Night One Dark's value. That is how the lint squiggles, grid edit tints and `.conn-dot` haloes drifted. Same trap in reverse: never hard-code a hex outside section 1.
- **Native widgets need `color-scheme`, not CSS colors.** The `<select>` **popup**, scrollbars, and checkboxes are painted by the WebView, not by our CSS — styling the select box (`background: var(--bg)`) does nothing for the popup. `:root` declares `color-scheme: dark` and `:root[data-mode="light"]` declares `light`; without it the popup renders light while `<option>` inherits the dark theme's near-white `--text` (white on white). Explicit `select option, select optgroup` colors are belt-and-braces for webkit2gtk. Keep `color-scheme` keyed to `data-mode`, not to `data-theme` — polarity, not palette.
- **Lint squiggles: SVG background, not `text-decoration: wavy`.** WKWebView (the macOS Tauri runtime) renders `text-decoration-style: wavy` unreliably. `.cm-lintRange-{error,warning,info}` in `App.css` use a repeating inline-SVG wavy underline (CodeMirror's own mechanism), recolored. Don't set `background: none` on those (it removes the squiggle), and don't rely on `wavy` text-decoration. Lint diagnostics are generated by the client (heuristic+schema) + server linters regardless — this is purely the *painting*.
- **Export parity + scope.** `export_to_file` accepts one safe read query (all rows) or validated inline rows (loaded). `formatWithOptions` must remain byte-parity with Rust for delimiters/null/header/projection/line endings/booleans and source-dialect SQL literals/identifiers. JSON object output requires unique columns. Every file path is sibling-temp + sync + atomic replace; empty results replace stale destinations with valid configured output, failure/cancel preserves the old file. Query export cancellation covers type discovery + paging; loaded-row/clipboard formatting has no armed DB operation and is bounded instead. xlsx is constant-memory and rolls sheets at 1,048,576 rows.
- **`validate_sql` never executes.** It uses checked `script::parse`, then PREPARE/DEALLOCATE in autocommit after cursor rollback. It skips DDL/utility/COPY/transaction starters and runtime parameters; malformed COPY/psql meta input errors before PREPARE. The frontend skips server lint while any query/stream is active and above the 1m-character live-analysis cap. Position mapping still subtracts the PREPARE prefix and restores statement whitespace offsets.
- **Scope by `Backend::database_name()`, never `ConnectionConfig.dbname`.** `dbname` is the field the USER TYPED: blank for DuckDB/SQLite (path-based) and blank on Postgres whenever libpq defaults it. `database_name()` returns what the server reports — the same value `DbTree.database` (and therefore the sidebar and `aiContext().database`) carries: `current_database()` on PG/DuckDB, `database()` on MySQL, `DB_NAME()` on SQL Server, literal `main` on SQLite. **AI skills scope on this in both the panel and the Slack bot**; scoping on `dbname` made a database-scoped skill apply in the panel and silently vanish for the bot. `driver_conformance`'s `database_name_battery` pins `database_name() == build_tree().database` on all four engines.
- **Providers are data; wires and origin trust are code.** Provider id is the keychain account and must never be renamed. `providers.ts` resolves model-specific wire/base; `ai.rs` implements the four wire shapes. A keyed custom base requires explicit frontend origin approval and HTTPS, and saving writes the key with that exact origin; legacy raw keys work only at shipped provider origins. Slack must mirror the requested resolved base/wire, including an unapproved override so Rust fails closed rather than silently rerouting context. `/models` success is not credential proof; keyed Test uses a tiny completion.
- **An SSE frame that isn't a delta is not nothing.** Providers report failures *inside* a `200 OK` stream (Anthropic `{"type":"error"}` for overloaded/rate-limit, OpenAI `{"error":{…}}`, Gemini `promptFeedback.blockReason`) and report truncation via a stop reason (`max_tokens`/`length`/`MAX_TOKENS`). The original parser matched only the delta pointer and treated everything else as `Ignore`, so a mid-stream failure ended the loop and emitted **`Done`** — the UI showed a truncated reply as a finished one, and Slack turned a half-written (unclosed ```sql fence) reply into the hardcoded "I can't help with that from Slack — try the Tusk desktop editor," blaming the user's question for a provider outage. When adding a provider, wire up **all three** of `extract_delta`/`extract_error`/`extract_finish` and add its frames to `ai.rs`'s tests; a provider whose errors you don't parse fails silently, which is strictly worse than failing loudly. Two traps: `"error": null` on every frame (vLLM/LiteLLM) is not an error, and a frame can carry a delta *and* a finish reason at once (Gemini's last chunk) — hence `Frame` is a struct, not an enum. Retry only replays when nothing has been painted yet (`soft_fail(msg, emitted && partial_is_fatal)`); the streaming path must never re-stream over visible text.
- **Slack bot invariants.** No query runs without a scoped, requester-only Approve click. Action ids are random capabilities but must also match allowlists/workspace/channel/thread/exact message/TTL and the proposal connection/database. SQL is one wrappable read, mutation/lock/output/executable-comment free, and limited to common deterministic unqualified built-ins; validate at proposal and execution. Run only on a fresh engine-enforced read-only backend, never shared cursor/session — **SQL Server is refused outright** (at the question and again at approval) because `read_only` buys it nothing server-side, and the wrap is per engine (`SELECT TOP n` on T-SQL, which has no `LIMIT`). Ack before work and dedupe event ids. PostgreSQL timeout cancels server-side; MySQL may continue after timeout; embedded calls are synchronous. Samples default off. Autostart binds to a saved profile id, never to whichever connection opens first, and a disconnect never rewrites the config. Config reloads per event; token replacement restarts. `slack/context.rs` remains parity-bound to AI context/skills.
- **In-grid editing: pending overlays, strict provenance.** Snapshot rows never mutate; Apply/Commit WHERE uses original PK values and generated scripts remain atomic in the app-owned or existing outer transaction. Edit only a single plain table with unique/non-case-colliding metadata, complete PK, and select items limited to `*`, `t.*`, `col`, or `t.col`; reject CTE/table/values, joins (including comma), expressions/aliases, derived/table-function sources, mismatched qualifiers, and unresolved/multi-table nested refs. Generation-bound menus/paste cannot target replaced results; transaction id/revision must still match; each edit action caps at 100k rows. Paste validates row identity/order and unique header mapping. Defense-in-depth still blocks non-table columns, cols-mode deletes, empty commits, and insufficient permissions.
