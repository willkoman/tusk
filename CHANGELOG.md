# Changelog

All notable changes to **Tusk** (fast native Postgres-first DB client). Format loosely follows Keep a Changelog. Newest first.

## [Unreleased]

### Added
- **The results grid now says what kind of data it is showing.** Each header carries a small type badge — the driver's own type where Tusk knows the relation, a dotted badge guessed from the loaded values otherwise. Numeric columns align right on tabular figures so magnitudes line up, booleans render as a glyph plus TRUE/FALSE, and a value over 300 characters is cut in the cell with a hover for its head. JSON and JSONB open pretty-printed in the value viewer. None of this touches the data: copy and export still write the raw driver text.
- **Record view: the focused row as a field list.** **Record** in the result toolbar (`Ctrl/⌘+Alt+V`) docks a panel beside the grid with one line per column — name, type badge, value. **‹** and **›**, or Alt+↑ / Alt+↓, step through rows, and the panel follows the focused cell. Where the grid is editable the fields are editable, through the same pending-change overlay and the same column rules as in-grid editing.
- **Find in loaded rows.** **Find** in the result toolbar, or `Ctrl/⌘+F` with the grid focused, opens a bar labelled *Find (loaded rows)*: a case-insensitive match across the rows already in memory, with every hit highlighted, the current one framed, a `3 of 128` counter, and Enter / Shift+Enter to step. It never re-runs the query — the **Filter** button next to it is still the server-side one.
- **Freeze the first column, and hide the row numbers.** Both live in the header right-click menu, alongside autofit and hide. A frozen first column stays at the left edge while the rest scroll sideways; with row numbers off the gutter narrows but still selects rows. Both survive a re-run of the query.
- **Copy as… now covers six shapes.** The cell menu's **Copy as…** offers TSV, CSV, JSON, Markdown, SQL INSERT, and column names only. INSERT statements name the edit target table when the result has one and use the connected engine's identifier and literal syntax, through the same formatter Export uses — so what you paste matches what an export would have written.
- **Selection facts in the status bar.** The right of the status bar shows the focused cell as `R n, C n`, the size of a multi-cell selection, and — when every non-NULL value selected is a number — Sum, Avg, Min, Max and Count over the loaded rows. With the results panel collapsed it also carries the last run's duration.
- **Organise the tab strip: rename, pin, colour.** Double-click a tab title (or right-click → *Rename…*) to retitle it inline; Enter keeps it, Escape cancels, and clearing the box brings the automatic title back. The custom title survives a Save as. *Pin tab* moves a tab into a fixed group at the left of the strip, shrinks it to its mascot and the first few characters of its name, and takes it out of every close-many action; pinned and unpinned tabs cannot be dragged past each other. *Colour* tags a tab with one of six theme-aware swatches, shown as a dot that stays clear of the transaction marker and the connection tint. Titles, pins and colours persist per connection with the rest of the tab set.
- **A fuller tab context menu.** Right-clicking a tab now offers Rename, Pin/Unpin, Colour, Copy path (file tabs), Close, Close others, Close tabs to the right, Close saved tabs, and Show all tabs. Every close-many action applies the same guards a single close does — unsaved buffers, pending grid edits, a running query, and a tab that owns a manual transaction are skipped, not forced — and the statusbar says how many closed and how many were kept.
- **Find any open tab from one list.** `Ctrl/⌘+Shift+O`, or the **⌄** beside the tab strip, opens **All tabs**: every open tab grouped by connection, with pin and unsaved markers, a filter box that matches the title, the file path and the connection name, and ↑/↓/Enter to pick. The strip scrolls and hides tabs; this list never does.
- **Settings → Appearance now covers the whole look.** Theme and accent are joined by **Density** (Comfortable or Compact, driving row, tab, tree and control heights everywhere at once, the result grid included), **UI scale** (90–125 % in 5 % steps, interface only — the editor keeps its own font size), **Explorer side** (left or right), the editor/grid font, editor font size, and a new **editor line height**. Everything applies live and persists, and **Reset to defaults** puts the whole pane back.
- **Open several databases at once.** The topbar now carries a strip of connection chips — one per open session, each with its driver's mascot, the database name and a state dot (idle, query running, transaction open, recovery required, session lost). Click a chip to switch, **✕** to disconnect just that one, **＋** to open the connect screen as a panel over your workspace instead of leaving it. Hovering a chip names its state, and while a query is running there the dot is a button: click it to cancel that connection's query — with a confirmation, and without switching to it first. Disconnecting a connection that is still running a query is refused until you cancel it or let it finish, so a stray click on **✕** can't kill a twenty-minute statement. Editor tabs are tagged with the connection they run against, and clicking a tab switches to its connection, so the Explorer, the transaction bar, permissions and autocomplete always describe the database the tab in front of you actually talks to. Up to 16 connections can be open at a time. With one connection open the strip looks as it always did — no mascot, no tint, no **✕** — apart from the new **＋** at the end of it.
- **Connections are genuinely independent.** A query on one connection no longer interrupts a result still streaming on another, and refreshing one Explorer no longer discards another connection's in-flight metadata. Each connection keeps its own result cursor, its own manual transaction and transaction bar, its own schema/function/foreign-key caches, its own tab set and recovered editor buffers, and its own Cancel. Opening the same saved connection twice gives each session its own tabs, so the second can neither inherit nor overwrite the first's unsaved work. Query history is the one deliberate exception: it is scoped to the *destination*, so two sessions on the same profile share a single combined history. Two connections can each hold an open transaction at the same time, and each connection to a different database gets its own "verify this unit's outcome" warning if Tusk is killed while they are open; closing one connection leaves the others exactly as they were, and closing the window asks you to resolve each open transaction in turn — and to confirm any *other* connection's pending grid edits before they are discarded.
- **Reopen last session.** The connect screen offers to reopen the saved connections that were open when you last used Tusk, in the order you had them — and the offer now survives connecting one of them, appears in the **＋** panel too, and says how many are still left to open. Anything that fails to reopen (profile deleted, host unreachable, keychain entry gone) is reported by name with its own reason and stays in the offer so you can retry it. Closing connections one at a time remembers all of them, exactly as closing the window with them open does. It never reconnects on its own — passwords come from the keychain and a silent multi-connect on launch is a surprise, not a convenience — and ad-hoc connections you typed in without saving are deliberately not remembered.
- **The AI assistant's chat belongs to the connection it started on.** A conversation is about one database: its schema, its dialect, its skills. Switching connections while the panel is open now tags the thread — it says which connection it is about, offers **New chat**, and holds Send and **Open in editor** until you switch back or start a new one — rather than quietly answering follow-ups with another database's schema, or dropping SQL written for PostgreSQL into a tab that runs on MySQL.
- **Two new connection chords.** `Ctrl/⌘+Alt+→` and `Ctrl/⌘+Alt+←` move to the next and previous connection, and `Ctrl/⌘+Shift+N` opens another one. All three are rebindable in Settings → Shortcuts like every other action, and the two *switching* chords stay inert while only one connection is open.
- **Settings → Slack now says which connection the bot answers against, and lets you change it.** The bot binds to exactly one Tusk connection — the one that was in focus when it started — and stays on it no matter which tab you move to, so a question asked in Slack can't change database because you switched tabs in the app. While the bot is running with several connections open, a connection picker appears under the status card; the new target applies from the next question, and proposals already awaiting approval stay pinned to the connection that produced them. If that connection is disconnected, the bot stops and says so where you are — a red **Slack** badge in the statusbar with the reason in the status text, not just a line in Settings — and switches its own On/Off toggle back off, so it can't return on the next launch bound to whichever connection happens to open first.
- **Build result filters visually, with AND/OR groups instead of one contains box per column.** The results toolbar has a **Filter** button (`Ctrl/⌘+Shift+F`), the column header menu offers *Filter by this column…*, and the Explorer's *Filter rows…* opens a table with the per-column filter row up and, once that relation's column detail loads, the builder over it. A condition is a column, an operator, and its values — `=`, `≠`, `<`, `≤`, `>`, `≥`, `between`, `not between`, `in`, `not in`, `like`, `not like`, `ilike`, `starts with`, `ends with`, `contains`, `is null`, `is not null`, `is true`, `is false`, `is empty` — and the operator menu only offers what the column's type supports, with a type badge next to the name. Conditions group into ANDs of ORs (or ORs of ANDs): the dialog offers a nested **Group** button four levels deep, and a filter may not exceed eight levels or 200 conditions in total. Each row can be duplicated or removed, and the dialog shows the exact `WHERE` clause it will run as you build it. **Apply filter** re-streams the result through the server as before, **Copy WHERE** puts the clause on the clipboard, and **Open as query** drops the full wrapped `SELECT` into a new tab so you can keep editing it as SQL. The clause is generated per engine: identifiers are always quoted and values are always literals, `ILIKE` is native on PostgreSQL and DuckDB and becomes a `LOWER(…) LIKE LOWER(…)` comparison everywhere else (their default collations usually ignore case, but a `_bin`/`_cs` column does not, and *contains* has to mean the same thing on every engine), every LIKE-family comparison is made on the text form of the column so a `char(n)` never matches on its blank padding, `%` and `_` you type are escaped with `!` under an explicit `ESCAPE '!'` rather than a backslash (which MySQL rejects under `sql_mode=ANSI`), booleans emit `TRUE`/`FALSE` or `1`/`0` to match how each engine stores them, and only strictly numeric text is emitted unquoted against a numeric column. `≠` and `not in` exclude NULL rows the way SQL does — add an `is null` condition in an OR group when you want them back.
- **Active filters are now visible above the grid.** A slim bar lists one chip per condition — grouped exactly as the filter is, joined by AND/OR — with an ✕ on each to drop just that rule, the loaded row count (with a trailing `+` while rows are still streaming), and **Edit…** / **Clear all**. The per-column filter row still works and now feeds the same filter, so a quick contains match and a built condition are the same thing.
- **Reach a database through an SSH tunnel.** The connect form has an **SSH tunnel** section for PostgreSQL, MySQL, and SQL Server: tick it, give the SSH host, port, and user, and pick **Password**, **Private key** (with an optional passphrase and a file picker), or **SSH agent**. Tusk opens the tunnel first and then connects to the **Host** and **Port** in the form *as the SSH server sees them* — usually `localhost` — so no port has to be forwarded by hand and nothing extra has to be installed: the SSH client is built in. Saved connections remember the tunnel settings, and the SSH password or key passphrase goes into the OS keychain under its own entry, with the same rule as the database password — change the SSH host, port, user, authentication method, or private-key file and you are asked to enter it again. Connections reached this way are marked **SSH** in the topbar and in the connections list, and the tunnel is re-established automatically if the link drops. `sslmode=verify-full` works through a tunnel on all three of those drivers: the certificate is checked against the database host you configured, not against the loopback address the tunnel listens on.
- **First contact with an SSH host asks you to confirm its fingerprint.** Tusk checks the server's host key against your `~/.ssh/known_hosts` — plain, `[host]:port`, comma-list, wildcard, negated and hashed entries, read-only; Tusk never writes to it — and against its own trust store. A host you have not seen before stops the connection and shows the key type and its `SHA256:…` fingerprint, so you can compare it against the server before choosing **Trust and connect**. A host whose key has *changed* is refused outright with no accept button: that is what a man-in-the-middle looks like, and clearing it is a deliberate act outside the connect screen. If the file cannot be read at all the connection is refused rather than treated as a first meeting. A key listed under `@revoked` is refused and never offered for trust, with two documented precedences: a key you have already accepted into Tusk's own trust store is checked first, and `known_hosts` is read in file order, so a plain entry for the same key above the `@revoked` line wins. `@cert-authority` lines are parsed and then skipped — Tusk does not verify host certificates yet, so a CA-covered bastion still prompts as an unknown host.
- **Backup and restore, built in — no `pg_dump`, no `mysqldump`, nothing to install.** Right-click a database, schema, or table in the Explorer (or use **Backup…** in the toolbar's ⋯ overflow, which appears when the editor pane is narrow) to write a plain-SQL dump through the driver Tusk is already connected with, on all five engines. Pick the scope from a searchable checklist, choose schema+data / schema only / data only, optionally emit `DROP … IF EXISTS` ahead of the creates or wrap the whole file in one transaction, and watch the object, row, byte and elapsed counters while it runs — with a Cancel that works on every engine, including the ones with no server-side query cancel. The dump is written to a sibling temp file and atomically renamed, so a cancelled or failed backup leaves your previous file exactly as it was. PostgreSQL reads through `COPY … TO STDOUT` inside one repeatable-read snapshot and writes `COPY … FROM stdin` blocks, so no table is ever held in memory; DuckDB, SQLite, MySQL and SQL Server page into batched multi-row `INSERT`s with the same quoting and literal rules as SQL export, and binary columns keep their native blob literals. On PostgreSQL, MySQL and SQL Server every foreign key is emitted after all the data — lifted out of PostgreSQL's and SQL Server's reconstruction and out of MySQL's `SHOW CREATE TABLE` — so a restore cannot fail on table ordering, cycles included. SQLite and DuckDB have no `ALTER TABLE … ADD CONSTRAINT`, so their foreign keys stay inline: a SQLite dump that carries schema turns enforcement off for the replay, and a cycle neither engine can order around is called out in the dump and in the result. PostgreSQL sequences come back at their real positions instead of restarting at 1, including in a table-scope backup, where the sequences a `serial` column depends on are dumped alongside it. Functions and triggers are reconstructed on PostgreSQL only; on the other engines the dump says so in a `-- warning:` line and in the result panel, with a count of the routines it could not carry.
- **Restore from file replays a dump statement by statement, and says exactly where it stopped.** **Restore from file…** (Explorer database node, or the ⋯ overflow) reads the dump's header first and shows the engine, database and timestamp it was taken from, warning up front when that engine is not the one you are connected to. Choose stop-at-first-error or keep going, optionally run everything in one transaction that rolls back on failure, and follow statements run, rows copied (`COPY` blocks only, so the row counter moves for PostgreSQL dumps and the statement counter for the rest) and bytes read live. The dialog also warns before you start if the file begins with a `psql` directive such as `\restrict` (Tusk replays SQL, not `psql` commands), and a byte-order mark left by a Windows editor no longer breaks the first statement. The result names the first failure with its statement number and line, and the sidebar and autocomplete reload afterwards. The file is parsed as it streams, so a gigabyte-scale dump never has to fit in memory: a restore reads at most 2 GiB and buffers at most 256 MiB for one statement or one `COPY` block. Restore is refused on read-only connections and while a manual transaction owns the session, and a statement is never replayed after the server may have seen it.
- **Import is now a guided, multi-step flow.** *Import data* (the Explorer toolbar icon, a table's *Import data into table…*, or a schema or database node's *Import file as new table…*) opens a three-step dialog on PostgreSQL, MySQL, SQLite and DuckDB. **1. File** picks the file, sets its parsing options and shows a sample of the parsed rows (50 parsed, 20 shown) with the detected columns and any warnings; **2. Columns** maps the file's columns onto a target; **3. Run** watches the load. Files are read and parsed in Rust straight from disk — nothing is loaded into the page and shipped over IPC — with live progress, a working **Cancel & roll back**, and a result summary. CSV/TSV gains a configurable delimiter, quote and escape character (leave Quote blank for a file with bare quotes in unquoted fields), a UTF-8 (BOM-tolerant) or Latin-1 encoding choice, a *skip N rows* preamble option, and a NULL text placeholder; JSON accepts both an array of objects and NDJSON; **xlsx** files can be imported directly, with a sheet picker. The `CREATE TABLE`, the optional clear and every batch run in one transaction: PostgreSQL streams a plain load through `COPY … FROM STDIN` and the other engines batch multi-row `INSERT`s. MySQL is the one exception, and says so: because MySQL commits DDL immediately, a create-and-load import creates the table as a separate, already-committed step before the rows load, so a failure rolls the rows back but leaves the empty table for you to drop.
- **Import into an existing table, with column mapping and conflict handling.** In the **Columns** step, file columns are auto-matched to target columns by name (case- and punctuation-insensitive), then adjustable by hand, including skipping a column entirely and per-column *empty string → NULL*. You can empty the table first, and choose what happens on a key conflict: fail, skip the row, or update it — `ON CONFLICT DO NOTHING` / `DO UPDATE` on PostgreSQL, `INSERT IGNORE` / `ON DUPLICATE KEY UPDATE` on MySQL, `INSERT OR IGNORE` / `OR REPLACE` on SQLite and DuckDB. Importing into a new table now infers a type per column (integer, bigint, numeric, boolean, date, timestamp, text) from the sampled values instead of creating everything as text, and every inferred type can be overridden before the table is created. Inference is deliberately conservative — a number too wide for a 64-bit integer stays `text`, a column already near the 32-bit limit widens to `bigint`, and a blank cell is a blank, not a value — so the type shown in the preview is one the load can actually use.
- **Export straight from the Explorer.** A table offers **Export table…**, and a view or materialized view **Export…**, which opens the usual configurator against that relation's full contents. A schema or database node offers **Export tables…**: tick the tables you want, choose a format, pick a directory, and get one configured file per table with per-table progress and a Cancel that works on every engine. Each file is written atomically, and a table that fails is reported by name while the run carries on with the rest — nothing already written is deleted.
- **Export the current grid selection.** With rows selected, the export dialog offers **Selection** alongside *All rows* and *Loaded rows*, to a file or the clipboard. Like *Loaded rows* it exports the stored values, so unapplied edits and pinned new rows stay out of the file.
- **Microsoft SQL Server is now a connectable driver.** Pick **SQL Server** on the connect screen (default port 1433) and sign in with a SQL login — the password goes to the OS keychain like every other network connection, TLS follows the same `sslmode` choices (`disable` sends plaintext, `prefer`/`require` encrypt without checking the certificate, `verify-full` also validates it), and read-only connections block writes and DDL. Windows integrated authentication isn't supported yet and says so instead of failing obscurely. The Explorer shows schemas, tables and views with row counts, and sizes on tables — a view has no storage of its own — plus columns with types, defaults, identity and primary/foreign-key marks, indexes, constraints, triggers, sequences, procedures and functions. Copy DDL reconstructs a table's `CREATE` (plain indexes included, foreign keys as trailing `ALTER`s) and returns the stored text for views, procedures and functions. The ERD, in-grid editing, export in every format, backup and restore (identity columns included, bracketed with `SET IDENTITY_INSERT`; foreign keys deferred past all data so a cycle restores; schemas recreated with T-SQL's guarded `IF SCHEMA_ID(…) IS NULL EXEC('CREATE SCHEMA …')`), and multi-statement scripts inside one transaction all work as they do elsewhere.
- **Paging on SQL Server keeps your ordering, or says when it can't page at all.** T-SQL has no `LIMIT`, so Tusk appends `OFFSET … ROWS FETCH NEXT … ROWS ONLY` to the statement: a query that already has an `ORDER BY` keeps exactly that order across pages, and one without gets the no-op `ORDER BY (SELECT NULL)` — the same "unordered pages" caveat MySQL has. A shape that cannot take the clause (`TOP`, its own `OFFSET`/`FETCH`, `FOR JSON`/`FOR XML`, `OPTION (…)`, or an unordered `UNION`) is read once under the usual result limits and labelled "read in one page" rather than paged wrongly.
- **What SQL Server doesn't do yet.** Four things are refused with their reason rather than half-working: file import isn't wired up for SQL Server; the Explorer's create/alter/drop items are disabled, because there are no T-SQL DDL builders yet; the Slack bot won't run a query against it, because `read_only` gives PostgreSQL, DuckDB, SQLite and MySQL a server-side guarantee and SQL Server nothing, so Tusk will not run an approved query there on SQL classification alone (everything else about the bot is unchanged); and Explain is disabled, because T-SQL has no `EXPLAIN` and Tusk can't render SHOWPLAN output yet. Two narrower limits: reconstructing a **table**'s DDL needs SQL Server 2017 or later and refuses on an older server rather than emitting a script with the keys silently missing (stored view, procedure and function text still works there), and grid sort and filter — which wrap the query as a derived table — are unavailable for any statement containing `WITH` or `ORDER BY` outside a literal or comment, table hints such as `WITH (NOLOCK)` and window ordering included, because T-SQL rejects both inside one.
- **The editor speaks T-SQL.** `[bracketed identifiers]` (with `]]` escapes), `N'unicode literals'`, nested `/* … /* … */ … */` comments and `GO` batch separators are understood everywhere it matters — statement splitting, the run gutter, folding, linting, parameter detection and grid wrapping — so a semicolon inside `[a;b]`, or a `GO` on its own line, no longer chops a statement in the wrong place. `GO` ends a batch without being sent to the server — with or without a trailing `--` or `/* … */` comment — and a `GO 5` repeat count is refused rather than silently run once. A `;` inside a T-SQL block (`BEGIN … END`, `BEGIN TRY`/`BEGIN CATCH`, `CASE … END`) is part of the statement, so `CREATE PROCEDURE` bodies, `IF`/`WHILE` blocks and `TRY`/`CATCH` run as written instead of being chopped into fragments. Highlighting and autocomplete use SQL Server's own keywords, types and functions (`TOP`, `OFFSET`/`FETCH`, `TRY_CAST`, `IIF`, `STRING_AGG`, `DATEADD`, `NVARCHAR`, …).
- **Manual transactions on SQL Server use T-SQL's own vocabulary.** `BEGIN TRANSACTION`/`BEGIN TRAN`, `COMMIT`, `ROLLBACK`, `SAVE TRANSACTION name` and `ROLLBACK TRANSACTION name` drive the transaction bar and its Commit/Rollback buttons, and Tusk checks `@@TRANCOUNT` and `XACT_STATE()` after every statement, so a transaction the server ended or doomed underneath you is reported instead of silently accepted. A bare `BEGIN`/`END` is treated as the statement block it is, not a transaction, and `ROLLBACK TRANSACTION <name>` that names the open transaction ends it instead of being mistaken for a savepoint. When SQL Server itself ends the unit — a deadlock victim, or any error under `XACT_ABORT ON` — you get the server's own message and the transaction bar returns to idle, rather than being told the connection dropped. `RELEASE SAVEPOINT`, `SET TRANSACTION ISOLATION LEVEL` and `SET IMPLICIT_TRANSACTIONS` are explained rather than sent — SQL Server has no per-transaction equivalent.
- **Create a table with the whole common surface, in any engine's dialect.** *Create table…* now covers per-column type (offered from the connected engine's own type list), NOT NULL, default expression, primary key (single or composite), unique, check, and auto-numbering in that engine's form — PostgreSQL `GENERATED BY DEFAULT AS IDENTITY`, MySQL `AUTO_INCREMENT`, SQLite `INTEGER PRIMARY KEY AUTOINCREMENT`, DuckDB a sequence created alongside the table. Column rows reorder with ↑/↓ and duplicate with ⧉, and an expandable section adds per-column checks and comments, foreign keys, `IF NOT EXISTS`, `TEMPORARY`, and MySQL's `ENGINE` / charset / collation. The SQL preview switches dialect with the connection.
- **Foreign keys are defined with a picker instead of typed out.** In *Create table…*, *Modify table…* and *Add constraint…*, choosing FOREIGN KEY gives a searchable `schema.table` box fed by the tree you already loaded; picking a table fetches its columns so **key columns come first and are marked** `pk` or `unique`. Composite keys add one local→referenced row at a time, `ON DELETE` / `ON UPDATE` and `DEFERRABLE` appear where the engine has them, and a local/referenced type that looks incompatible raises a warning rather than blocking you — the engine has the final say.
- **Modify table does more, and says what it will do.** The diff editor now reorders columns, adds UNIQUE / CHECK / foreign-key constraints, drops each constraint kind with the action that engine actually uses, and on PostgreSQL moves the table to another schema. It refuses to run on an empty column name, on a duplicate one — case-insensitively on DuckDB, MySQL and SQLite, which treat two spellings of a name as one column; PostgreSQL is left alone, because Tusk always quotes identifiers and `"Id"` and `"id"` are two legal columns there — or on a nullable primary key, except on SQLite, which genuinely allows NULLs in a non-INTEGER key. It also refuses to rewrite a generated column, whose expression no `ALTER` here can restate, and says which column and why. Column reordering is offered only on SQLite, the one engine that can express it. When the generated script is more than one statement, a note underneath says how it runs — plainly, when it is not atomic, as on MySQL, where every DDL statement commits itself.
- **SQLite tables can be changed, not just renamed.** SQLite's `ALTER TABLE` only renames the table, renames a column, adds a column and drops one. For anything else — a type change, a NOT NULL or default change, a key change, a constraint edit, a column reorder, or dropping a column SQLite refuses to drop in place — Tusk now generates the documented rebuild: create the new shape, `INSERT … SELECT` the rows, drop the original, rename the replacement into place, recreate the indexes and triggers. It runs as one transaction, the preview is labelled as a rebuild and the button reads **Rebuild table**. Everything the rebuild has to recreate comes from the table's stored definition, so CHECK constraints (a table-level one keeps its name; one written inside a column definition comes across unnamed), column collations, generated columns and `WITHOUT ROWID` / `STRICT` survive it rather than disappearing — and the drop-and-rename is wrapped in `PRAGMA legacy_alter_table`, so a table another view or trigger refers to can be rebuilt at all. Where a rebuild cannot be done safely, Tusk refuses it and says why instead of running a script that fails half-way: a rename in the same pass as a rebuild (apply the rename on its own first), dropping a column an index, constraint or trigger still uses (drop that too), and a stored definition Tusk could not read. A table's triggers are replayed verbatim, semicolons in their bodies and all, and because dropping the original would orphan any row that references it, foreign-key enforcement is switched off for the rebuild and back on immediately after — SQLite ignores that setting inside a transaction, so it has to happen around one. The dialog says so before you run it.
- **The Explorer's DDL menu works on MySQL and SQLite.** Create table / column / index / constraint, modify, rename, drop, truncate, duplicate and comments are live on PostgreSQL, DuckDB, MySQL and SQLite instead of PostgreSQL and DuckDB only. Each action is offered only where the engine can express it, and the tooltip names the engine — *"MySQL can't rename a constraint"*, *"SQLite can't create a schema"* — while a read-only connection or an open transaction keeps saying so rather than being relabelled with the weaker engine reason. MySQL has no schema layer, so a "schema" there is a database: dropping one is labelled **Drop database…**, confirms as a database, and — like the database node — refuses to drop the one you are connected to. SQLite's *Truncate…* becomes *Delete all rows…* and runs `DELETE FROM`, which is SQLite's equivalent.
- **The Explorer shows a table's real indexes, constraints and comments.** MySQL, SQLite and DuckDB previously reported none of these, so expanding a table there showed only its columns. Each driver now reads them from its own catalog, including MySQL table and column comments, triggers, generated columns and `ON UPDATE CURRENT_TIMESTAMP`; SQLite's foreign keys, unique and CHECK constraints, column collations, generated columns and triggers; and DuckDB's table and column comments, which were previously write-only — you could set one and it would never come back. Comments show wherever the engine has them (PostgreSQL, DuckDB, MySQL and SQL Server); SQLite has no `COMMENT` syntax at all. A foreign key declared as a bare `REFERENCES parent` is shown as written, rather than with an empty referenced column.

### Changed
- **Reordering tabs and result columns is one proper drag.** Picking up an editor tab or a grid column header lifts a ghost of it under the pointer — the tab's mascot, connection tint, title and unsaved dot included — dims the original in place, and marks the landing slot with an accent bar that slides between positions. The order changes only when you let go, so Escape, or a release outside the strip, leaves it as it was. Dragging near either end scrolls the strip or the grid, a 4 px threshold keeps a click a click (a header click still sorts), and a column drag still only changes what you see. `Alt+Shift+←` and `Alt+Shift+→` move the active tab one slot without the mouse, and are rebindable in Settings → Shortcuts.
- **SQL export can now include the real `CREATE TABLE`.** When the result is a plain table, *Include CREATE TABLE* reconstructs that table's actual DDL — types, keys, defaults — instead of the generated all-`text` stand-in. For a join, an expression or a script result it falls back to the generated form and says so.
- **The export dialog remembers your last options per format.** Delimiter, quoting, NULL text, line endings, BOM, header, multi-row INSERT and the Excel flags come back the way you left them the next time you pick that format; the column selection and table name still belong to the result being exported.
- **Dropping an index, constraint or column is now a named action, not a tick box.** In *Modify table…* each index, constraint and column row carries a **Drop** button. Operations DuckDB's engine genuinely can't do — adding/dropping constraints via `ALTER`, renaming an index/sequence/constraint, `CREATE DATABASE` — are disabled per-item with an explanatory tooltip. (Adding a NOT NULL column works on an empty table; on a populated one DuckDB surfaces its own "NOT NULL constraint failed", as it can't backfill-and-constrain atomically.) Covered by new builder unit tests + a DuckDB conformance battery that executes every generated form.

- **Streaming that broke mid-result failed silently.** When the connection dropped while paging a large result (idle timeout, server restart, network blip — the kind that logs `[tusk] postgres connection error: error communicating with the server` to the terminal), the rows simply stopped with no indication in the app. Two silent paths fixed: (1) `fetch_more`'s `ensure_alive` would re-open the dead connection — which discards the server-side cursor (it lived in a transaction on the old connection) — and then report `done: true`, presenting a truncated result as complete; it now detects the lost-cursor case (`was_streaming && !cursor_open`) and returns an error instead. (2) `loadMore`'s catch logged to the console and marked the result done; it now surfaces the message in the result error banner (over the rows fetched so far) and sets the status to `streaming stopped — …`, then stops paging. Re-run the query to load the rest.
- **Result grid jumped to the top on every mutation (and felt like sort/resize/reorder were "broken").** The grid's scroll/selection-reset effect keyed on `${tabId}:${epoch}`, but `on()` re-runs its callback whenever a tracked dependency *notifies* — not only when the value changes — and `epoch` is read through App's `activeTab()` memo, whose identity changes on every `patchTab`/`patchResult`. So appending a streamed page, resizing/reordering/hiding a column, or any other grid edit re-fired the effect, took the `switched === false` ("new query") branch, and slammed `scrollTop` back to 0 while clearing the selection — on each `mousemove` of a resize drag, no less. The key is now a `createMemo`, so it dedupes by string value and the reset fires only on a real tab switch or new-query epoch bump. Verified in the harness: append/resize/reorder while scrolled to row ~180 keep the scroll position (was → 0); a sort click still resets to top on purpose (it re-streams the wrapped query).
- **Result grid froze/crashed when scrolling a large table.** Every scroll frame persisted the scroll position into the per-tab `gridView` via `setView`, which rebuilt the tabs array and invalidated `activeTab` — cascading a full reactive recompute across the whole App (editor + every memo) on each frame, and forcing the grid's own column-geometry memos (`displayCols`/`offsets`) to recompute too. Scroll position now lives in a non-reactive per-tab `Map`; the local `scrollTop`/`scrollLeft` signals (which only the row/column window memos depend on) drive virtualization, and nothing writes to shared state on scroll. Verified on a 50-col × 200k-row grid: zero `setView` calls during a scroll burst, cell count stays windowed (~128–192), correct rendering at row 99,000 / far-right, frames ≤ ~10 ms.

### Fixed
- **Network failures fail fast; query duration is never capped.** A query on a dead connection used to spin on "Running…" indefinitely (TCP retransmit can take many minutes). Now a 10s **connect timeout** bounds the open/reconnect path and **aggressive TCP keepalives** (5s idle, 2s interval, 3 retries, 15s `tcp_user_timeout`) drop a genuinely dead connection in ~10-15s → the in-flight query errors and the next action auto-reconnects. A slow-but-alive query keeps getting keepalive ACKs and runs **as long as it needs** (no artificial timeout). The Run button shows a **live H:M:S counter** while a query runs.
- **Dropped connections now auto-recover.** When a Postgres connection was closed underneath the app (idle timeout, server restart, network blip), every subsequent action failed permanently with no way out but disconnect + reconnect. The backend now retains each connection's config (server-side only, never sent to the frontend) and **transparently re-opens** a closed connection on the next action (`ensure_alive`, gated on `Client::is_closed()`); `run_query` additionally reconnects + retries once if a query dies mid-flight. Verified end-to-end (terminate the backend server-side → `is_closed()` flips → next query reconnects and succeeds).
- **Native WebView right-click menu showed instead of the app menu** — the OS/WebView context menu is now suppressed app-wide (`document` `contextmenu` `preventDefault`), so right-click consistently opens the sidebar's own action menu (and nothing in the editor/grid).
- **Sidebar boolean flags were always false** — catalog queries cast booleans to `::text` (e.g. `(NOT a.attnotnull)::text`) and compared against `"t"`, but `bool::text` yields `"true"`/`"false"` (only a *bare* bool renders `"t"`/`"f"` over the text protocol). So every column showed as `NOT NULL`, and index `unique`/`primary` flags were wrong. Found via GUI test against a real DB. Fixed by dropping the `::text` casts (tree.rs `table_detail`, ddl.rs `object_ddl`). This also fixed Copy DDL emitting constraint-backed PK/unique indexes (the `backs` dedup flag was stuck false → duplicate-index errors on replay) and omitting `NOT NULL`/`DEFAULT`.
- **Tall context menus ran off the bottom of the window** — the open-position clamp under-estimated menu height, clipping the last items. The menu now measures its real size after mount and shifts to stay fully on-screen.
- **`COPY … FROM stdin` after comment headers** — pg_dump prefixes each COPY with a `--` comment block, which made the script runner miss the COPY (it saw `--`), send it via `batch_execute`, and desync the protocol ("unexpected message from server"). COPY is now detected by the first non-comment token, and `copy_in` receives the comment-stripped statement.
- **Dollar-quoted function bodies corrupted by autocomplete** — Enter no longer silently accepts a completion (accept is **Tab-only**), and `$`-sigils (`$_$`, `$1`) no longer trigger completion. Fixes `CREATE FUNCTION … AS $_$ … $1 … $_$` failing with "syntax error at or near 1".
- **Empty export writes no file** — the output file is created lazily on the first row, so a 0-row result never touches disk.
- **Cropped UI on launch** — default window is now 1200×820 (min 900×600, centered); the connect screen scrolls if its form is taller than the window.
- **Error surfacing** — `tokio-postgres` errors previously surfaced as the useless string "db error"; now the real Postgres message (DbError) or source-chain detail is shown. Added a precise message when a saved keychain password can't be read in unsigned dev builds.
