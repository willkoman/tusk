# Tusk 0.7.0 — Slack Integration: Natural-Language → SQL → Result

> Implementation spec for an autonomous agent. Every section is actionable.
> Read `CLAUDE.md` first for the full architecture context. This doc builds on it.

## 1. Overview

### Goal

A user sends a plaintext question in Slack ("top 10 products by revenue last month") or ("find the highest performing products by sales count in third quarter of 2026"). Tusk's AI proposes a SQL query, posts it inline with Approve/Edit/Reject buttons. On approval, Tusk runs the query against the currently-connected database and posts the result back — either as a Slack table, a chart image (if the data is visual), or a file attachment (CSV/XLSX) for large results.

### Core Principles (non-negotiable)

1. **Human-in-the-loop.** No query runs without explicit Slack-button approval. The AI proposes; a human approves.
2. **Desktop app is the host.** The Slack bot runs inside the Tauri app as a background tokio task. No separate server binary, no deployment. The app must be running. (Future: headless mode.)
3. **Reuses existing infrastructure.** `driver.rs` for query execution, `export.rs` formatters for file output, `ai.rs` providers for completions, `keyring` for secret storage. No reinvention.
4. **Read-only by default.** The bot only proposes `SELECT` queries for Slack. Writes/DDL require the user to open the query in Tusk (deep-link). This is a v1 safety boundary.
5. **Data stays local.** The chart rendering uses QuickChart (configurable base URL — self-hostable). File attachments are generated locally. No query results or schema data leaves the machine except to the AI provider (already the case) and Slack (the user's own workspace).

### What This Is Not

- Not a standalone Slack app service. It's a feature of the Tusk desktop app.
- Not multi-connection. v1 uses the currently-active Tusk connection.
- Not background/push notifications for query completion on long-running queries. v1 is synchronous (with a timeout).

## 2. Architecture: Slack Socket Mode

### Why Socket Mode

Slack offers two integration models:
- **Events API**: Slack sends HTTP POSTs to a public URL. Requires a public endpoint (ngrok, cloud tunnel). Bad for a desktop app.
- **Socket Mode**: Slack sends events over a WebSocket. The app connects outbound — no public endpoint, no tunnel, no inbound HTTP server. Designed for apps like this.

Socket Mode is the clear choice. The app opens a WebSocket to Slack, receives events, and posts responses via Slack's Web API (outbound HTTPS, reusing the existing `reqwest` client).

### Lifecycle

```
App launch
  └─ if Slack enabled in settings:
       └─ spawn tokio task: `slack::run_socket_mode(bot_token, app_token)`
            ├─ connect WSS to wss://wss-primary.slack.com
            ├─ on envelope:
            │    ├─ type:"hello"       → connected
            │    ├─ type:"events_api"  → dispatch event (message, app_mention)
            │    └─ type:"interactive"  → dispatch interaction (button click)
            └─ reconnect on disconnect (exponential backoff)
```

The task runs on `tauri::async_runtime::spawn`. It holds no Tauri state directly — it communicates with the app via a `tokio::sync::mpsc` channel of `SlackEvent`s, and the Tauri command layer processes them. This keeps the WebSocket client pure and testable.

### New Crate Dependencies

```toml
# src-tauri/Cargo.toml [dependencies]
tokio-tungstenite = { version = "0.24", features = ["rustls-tls-webpki-roots"] }
```

That's the only new external crate. Everything else (`reqwest`, `serde_json`, `tokio`, `futures-util`, `keyring`) is already in the tree. `tokio-tungstenite` provides the WebSocket client. No `axum`, no HTTP server.

**Tokio runtime:** Tauri's `async_runtime` provides a single-threaded runtime by default. The Slack WebSocket task is long-lived and mostly I/O-bound (wait for event → process → post). Single-threaded is fine. If profiling shows contention, add `rt-multi-thread` to the `tokio` dep — but try without it first.

### 4.2 `slack/socket.rs` — Socket Mode Client

The WebSocket client. Responsibilities:
- Connect to `wss://wss-primary.slack.com/?token={app_token}`
- Receive JSON envelopes: `{"type":"hello","num_connections":…}`, `{"type":"events_api","payload":{…}}`, `{"type":"interactive","payload":{…}}`
- Acknowledge each envelope by sending back `{"type":1}` (Slack's ack payload ID — read the `envelope_id` from each envelope and ack with `{"envelope_id":"…"}`)
- Dispatch payloads to an `mpsc::Sender<SlackEvent>`
- Reconnect with exponential backoff (1s, 2s, 4s, …, max 60s)
- Clean shutdown via a `CancellationToken`

```rust
pub enum SlackEvent {
    Message { channel: String, user: String, text: String, thread_ts: Option<String>, ts: String },
    AppMention { channel: String, user: String, text: String, thread_ts: Option<String>, ts: String },
    Interaction { payload: serde_json::Value },  // button clicks — parsed by approval.rs
    Connected,
    Disconnected(String),  // error message
}

pub async fn run_socket_mode(
    app_token: String,
    tx: mpsc::Sender<SlackEvent>,
    cancel: tokio_util::sync::CancellationToken,
) -> Result<(), AppError>;
```

**Crate note:** Use `tokio-tungstenite` for the WebSocket. The protocol is simple enough that a raw client is cleaner than pulling in `slack-morphism` (which is large and opinionated).

**CancellationToken:** Add `tokio-util = { version = "0.7", features = ["rt"] }` to Cargo.toml (or use a simple `AtomicBool` + `tokio::select!` on a `oneshot` channel — either works; `CancellationToken` is cleaner).

### 4.3 `slack/api.rs` — Slack Web API Wrappers

Outbound HTTP calls to Slack's Web API using the existing `reqwest` client. All use the bot token (`xoxb-…`) as `Authorization: Bearer {token}`.

```rust
pub struct SlackApi { client: reqwest::Client, bot_token: String }

impl SlackApi {
    /// Post a message (text or Block Kit). Returns the message `ts` (for threading).
    pub async fn post_message(&self, channel: &str, text: &str, blocks: Option<serde_json::Value>) -> Result<String>;

    /// Update an existing message (replace content). Used for "thinking…" → proposal.
    pub async fn update_message(&self, channel: &str, ts: &str, text: &str, blocks: Option<serde_json::Value>) -> Result<()>;

    /// Add a reaction emoji to a message.
    pub async fn add_reaction(&self, channel: &str, ts: &str, emoji: &str) -> Result<()>;

    /// Upload a file and share it in a channel. Uses the new files.getUploadURLExternal flow:
    /// 1. files.getUploadURLExternal(filename, length) → upload_url + file_id
    /// 2. POST binary to upload_url
    /// 3. files.completeUploadExternal(file_id, channel) → shares the file
    pub async fn upload_file(&self, channel: &str, filename: &str, content_type: &str, data: Vec<u8>) -> Result<()>;

    /// Open a Slack modal view (for "Edit in Tusk" deep-link or advanced options).
    pub async fn open_view(&self, trigger_id: &str, view: serde_json::Value) -> Result<()>;
}
```

**File upload detail:** Slack is deprecating `files.upload` (the old single-call API). The new flow is:
1. `POST files.getUploadURLExternal` with `filename` + `length` (bytes) → returns `upload_url` and `file_id`.
2. `POST` the raw bytes to `upload_url` (Content-Type: `application/octet-stream` or the file's MIME).
3. `POST files.completeUploadExternal` with `files: [{id: file_id}]` and `channel_id` → shares the file in the channel.

This is 3 HTTP calls but handles files >1MB correctly (the old API had a 1MB inline limit).

### 4.4 `slack/blocks.rs` — Block Kit Message Builders

Pure functions that build `serde_json::Value` Block Kit payloads. No I/O.

```rust
/// The "thinking…" card — posted immediately while the AI generates SQL.
pub fn thinking_card() -> serde_json::Value {
    json!({
        "blocks": [{
            "type": "section",
            "text": { "type": "mrkdwn", "text": "🤔 *Generating query…*" }
        }]
    })
}

/// The proposal card — SQL + explanation + buttons.
/// `proposal_id` ties the buttons to a pending proposal in `approval.rs`.
pub fn proposal_card(explanation: &str, sql: &str, proposal_id: &str) -> serde_json::Value {
    json!({
        "blocks": [
            { "type": "section", "text": { "type": "mrkdwn", "text": format!("🤖 *Proposed query*\n{}", explanation) } },
            { "type": "section", "text": { "type": "mrkdwn", "text": format!("```sql\n{}\n```", sql) } },
            { "type": "actions", "elements": [
                { "type": "button", "text": { "type": "plain_text", "text": "✅ Approve" },
                  "style": "primary", "value": format!("approve:{}", proposal_id),
                  "action_id": "approve_query" },
                { "type": "button", "text": { "type": "plain_text", "text": "❌ Reject" },
                  "style": "danger", "value": format!("reject:{}", proposal_id),
                  "action_id": "reject_query" }
            ]}
        ]
    })
}

/// A result summary — posted alongside a table or file attachment.
pub fn result_summary(text: &str, row_count: usize, elapsed_ms: u128) -> serde_json::Value;

/// An error card.
pub fn error_card(message: &str) -> serde_json::Value;

/// A small result table — inline Block Kit sections.
/// Up to `max_rows_inline` rows, `max_cols` columns. Pipe-formatted mrkdwn.
pub fn result_table(columns: &[String], rows: &[Vec<Option<String>>]) -> serde_json::Value;
```

**Table formatting note:** Slack Block Kit has no native table type. For small results, use `mrkdwn` pipe-separated text inside a `section` block:
```
*product_name*          *revenue*
Widget Pro             $12,345.00
Gadget X               $8,901.00
```
Pad columns with spaces for alignment (calculate max width per column). Keep it monospace-friendly (Slack renders mrkdwn code blocks in monospace, but inline mrkdwn is proportional — wrap the table in a code block: `` ` `` ` `` ` ` `` ... actually, just use a single `mrkdwn` section with the table wrapped in triple backticks for monospace rendering).

**Better approach:** render the small table as a triple-backtick code block (monospace) inside a single `section` block. This gives perfect alignment with simple space-padding and avoids Slack's proportional-font table rendering issues.

### 4.5 `slack/approval.rs` — Pending Proposal Store

In-memory store of pending SQL proposals awaiting Slack button approval.

```rust
pub struct PendingProposal {
    pub id: String,           // UUID
    pub sql: String,
    pub channel: String,
    pub user: String,          // Slack user ID who asked
    pub thread_ts: String,     // for threading the response
    pub message_ts: String,    // the proposal message ts (for updating)
    pub created_at: Instant,
}

pub struct ApprovalStore {
    proposals: Mutex<HashMap<String, PendingProposal>>,
}

impl ApprovalStore {
    pub fn insert(&self, p: PendingProposal);
    pub fn take(&self, id: &str) -> Option<PendingProposal>;  // take = consume
    pub fn expire(&self) -> Vec<PendingProposal>;  // remove entries older than TTL (5 min)
}
```

**TTL:** 5 minutes. A background task (or lazy check on each interaction) expires stale proposals and updates their Slack messages to "⏰ Proposal expired".

**Interaction dispatch:** When a `SlackEvent::Interaction` arrives, parse the `actions[0].value`:
- `"approve:{id}"` → `take(id)`, execute the query, post results
- `"reject:{id}"` → `take(id)`, update message to "❌ Rejected"

Only the user who requested the query can approve/reject (check `user` against the proposal's `user` field). Other users get an ephemeral error ("Only the requester can approve").

**Token budgets (same as TS):**

**System prompt for Slack** differs from the desktop prompt in one key way: the AI should return a single SQL query in a ```` ```sql ```` block, preceded by a one-sentence explanation. The prompt explicitly says:

```
You are a SQL assistant connected to {driver_label} {version}.
A user asked a question in Slack. Generate a single read-only SELECT query.
Format your response as:
1. One sentence explaining what the query does.
2. The query in a ```sql code block.

Rules:
- Only SELECT queries. No INSERT/UPDATE/DELETE/DDL.
- Always quote identifiers.
- Use LIMIT when the user asks for "top N" or when the result could be large.
- If the question is ambiguous, make reasonable assumptions and note them in your explanation.
```

### 4.7 `ai.rs` — Add Non-Streaming Completion

The current `ai_chat` streams deltas over a Tauri Channel. The Slack bot needs the full response as a `String`. Add a sibling function:

```rust
/// Non-streaming AI completion. Collects all deltas and returns the full text.
/// Used by the Slack bot (which posts the complete response at once).
pub async fn ai_complete_one_shot(
    req: &AiRequest,
) -> Result<String, AppError> {
    // Same provider dispatch as build_request, but:
    // - Set "stream": false in the request body
    // - Read the full JSON response (not SSE)
    // - Extract the complete text per provider:
    //   - anthropic: content[0].text
    //   - openai: choices[0].message.content
    //   - gemini: candidates[0].content.parts[0].text
}
```

**Implementation note:** Rather than building two paths (streaming + non-streaming), you can reuse the existing streaming path and just accumulate deltas. The simplest approach:

```rust
pub async fn ai_complete_one_shot(req: &AiRequest) -> Result<String, AppError> {
    // Reuse build_request (which sets stream:true), then read the SSE stream
    // and accumulate all Delta text into a single String. Return on Done.
    // This avoids maintaining two request-body builders per provider.
    let (url, headers, body) = build_request(req, &get_key(&req.provider)?);
    // ... POST, read stream, accumulate ...
}
```

This is the pragmatic path — one request builder, two consumers (channel for frontend, accumulator for Slack).

### 4.8 `export.rs` — Add In-Memory Buffer Output

The current export sinks write to files. The Slack bot needs to produce CSV/XLSX in memory (for file attachments). Add:

```rust
/// Format inline rows to an in-memory buffer (no file I/O).
/// Used by the Slack bot to produce CSV/Markdown attachments.
pub fn export_rows_to_buffer(
    columns: &[String],
    rows: &[Vec<Option<String>>],
    opts: &ExportOptions,
) -> Result<Vec<u8>, AppError>;

/// Run a query and stream-format it to an in-memory buffer.
/// Used by the Slack bot for large result exports.
pub async fn export_query_to_buffer(
    backend: &mut Backend,
    sql: &str,
    opts: &ExportOptions,
) -> Result<(Vec<u8>, usize), AppError>;  // (bytes, row_count)
```

**Implementation approach:**

For text formats (CSV/TSV/JSON/Markdown/SQL), the pure formatters (`delim_field`, `header_text`, `row()`) already build `String`s before writing. Extract a `TextSink` that implements `AsyncWrite` over `Vec<u8>` (trivial — `Vec<u8>` implements `std::io::Write`; wrap in a simple adapter). The formatting logic is identical — only the sink changes.

For XLSX: `rust_xlsxwriter` can save to a `Vec<u8>` via `workbook.save_to_buffer()` (check the API — it exists). No tempfile needed.

**Alternative (simpler for v1):** Write to a tempfile (using `std::env::temp_dir()`) and read the bytes back, then delete the tempfile. This reuses the existing file-based code unchanged. The extra I/O is negligible for a Slack attachment (max ~10MB). If the existing `run_export_rows` / `run_export_query` already work with a file path, just:

```rust
pub async fn export_rows_to_tempfile(columns, rows, opts) -> Result<(PathBuf, Vec<u8>)> {
    let path = temp_dir().join(format!("tusk_slack_{}.{}", uuid, ext));
    run_export_rows(columns, rows, opts, &path).await?;
    let bytes = tokio::fs::read(&path).await?;
    tokio::fs::remove_file(&path).await.ok();
    Ok(bytes)
}
```

**Recommendation:** Start with the tempfile approach (no refactor to existing export code). Refactor to buffer output later if performance matters.

### 4.9 `slack/format.rs` — Result → Slack Format Decision

After a query executes, decide how to present the result in Slack.

```rust
pub enum ResultFormat {
    /// Small result — inline table in a code block.
    InlineTable,
    /// Medium result — CSV file attachment.
    CsvAttachment,
    /// Large or wide result — XLSX file attachment.
    XlsxAttachment,
    /// Chart-able result — QuickChart PNG image attachment.
    ChartImage { config: serde_json::Value },
    /// No rows — just a count/message.
    Empty { message: String },
}

pub fn decide_format(
    columns: &[String],
    rows: &[Vec<Option<String>>],
    elapsed_ms: u128,
    config: &SlackConfig,
) -> ResultFormat;
```

**Decision tree:**

1. **0 rows:** `Empty` — post "✅ Query completed in {ms}ms. No rows returned."
2. **≤ `max_rows_inline` (default 20) rows AND ≤ 5 columns:** `InlineTable` — post a code-block table.
3. **Chart-able** (see chart detection below): `ChartImage` — generate a QuickChart config and post a PNG.
4. **≤ `max_rows_file` (default 10,000) rows:** `CsvAttachment` — post a CSV file.
5. **> `max_rows_file` rows OR > 15 columns:** `XlsxAttachment` — post an XLSX file.

**Chart detection heuristic (v1 — simple, improve later):**

A result is "chart-able" if:
- ≥ 2 columns AND ≤ 4 columns
- First column looks like a date/timestamp (name contains `date`, `time`, `created`, `month`, `year`; or values match a date regex)
- Remaining columns are numeric (all values parse as f64 or are null)
- ≤ 50 rows (larger datasets should be files, not charts)

If chart-able, build a QuickChart config:
```json
{
    "type": "line",  // or "bar" if ≤ 12 rows
    "data": {
        "labels": [<first column values>],
        "datasets": [
            { "label": "<col name>", "data": [<values>] }
            // one dataset per numeric column
        ]
    },
    "options": {
        "responsive": true,
        "plugins": { "title": { "display": true, "text": "<query summary or 'Query Results'>" } }
    }
}
```

POST this to `{quickchart_url}` (default `https://quickchart.io/chart`) → get back a PNG → upload to Slack.

**Privacy note:** QuickChart sends chart data (labels + values) to an external service. The chart config contains no schema info (just data values), and it's the user's own data going to a chart renderer. Document this. If the user sets `quickchart_url` to a self-hosted instance, data stays local. The settings UI should surface this clearly.

**Event processing loop (in `lib.rs` or a `slack/processor.rs`):**

```rust
async fn process_slack_event(
    event: SlackEvent,
    api: &SlackApi,
    app_state: &AppState,
    approval_store: &ApprovalStore,
    config: &SlackConfig,
) {
    match event {
        SlackEvent::Message { channel, user, text, thread_ts, ts } => {
            // 1. Check allowlist
            // 2. Get active connection from app_state
            // 3. Build AI context (schema, permissions)
            // 4. Post "thinking…" message (update later)
            // 5. Call AI one-shot
            // 6. Extract SQL from response
            // 7. Classify query (must be SELECT, read-only)
            // 8. Store pending proposal
            // 9. Update message → proposal card with buttons
        }
        SlackEvent::Interaction { payload } => {
            // 1. Parse action_id + value
            // 2. Look up pending proposal
            // 3. Check user matches
            // 4. If approve → execute query → format → post result
            // 5. If reject → update message
        }
        SlackEvent::AppMention { .. } => {
            // Same as Message but the text has the @mention stripped
        }
        SlackEvent::Connected => { /* update status signal */ }
        SlackEvent::Disconnected(err) => { /* update status signal, maybe alert */ }
    }
}
```

**Connection access:** The Slack bot needs access to the active Tusk connection. The app is single-connection, so:
- `AppState::conns` has all connections (usually one).
- The bot picks the first connection (or the one marked "active" by the UI — add an `active_conn_id: Mutex<Option<String>>` to `AppState`, set when the user connects).
- Lock the connection, call `ensure_alive`, run the query, release.

**Threading concern:** If the user is running a query in the Tusk UI and a Slack query comes in, they'll contend for the `AsyncMutex<ConnState>`. This is fine — the Slack query waits. The "thinking…" message is already posted; the user sees the query execute once the lock is available. Add a note to the thinking message: "Waiting for an available connection…" if the lock isn't immediately available.

## 5. End-to-End Flow

### 5.1 Question → Proposal → Approval → Result

```
Slack                                    Tusk (Tauri)
─────                                    ────────────

User: "top 10 products by revenue
       last month"
                    ──[Socket Mode WSS]──→  receive Message event
                                            │
                                            ├─ check allowlist ✓
                                            ├─ get active connection
                                            ├─ post "🤔 Generating query…"
                                            │    (save ts for update)
                                            ├─ build AI context:
                                            │    ├─ Backend::list_tables()
                                            │    ├─ Backend::permissions()
                                            │    ├─ relevant_tables(question)
                                            │    ├─ Backend::sample_rows(top 5)
                                            │    └─ build_system_prompt()
                                            ├─ ai_complete_one_shot(question + prompt)
                                            ├─ extract_sql_blocks(response)
                                            ├─ validate: must be single SELECT
                                            │    (use script::split + is_read_only_stmt)
                                            ├─ store PendingProposal {sql, channel, user, ts}
                                            └─ update message → proposal card
                                               (SQL + ✅ Approve / ❌ Reject)

User clicks "✅ Approve"
                    ──[Socket Mode WSS]──→  receive Interaction event
                                            │
                                            ├─ take proposal from store
                                            ├─ check user matches requester
                                            ├─ lock active connection
                                            ├─ ensure_alive
                                            ├─ tokio::time::timeout(
                                            │    Duration::from_secs(config.timeout),
                                            │    backend.run_single(sql, page, true)
                                            │  )
                                            ├─ on success:
                                            │    ├─ decide_format(columns, rows)
                                            │    ├─ match format:
                                            │    │    ├─ InlineTable → post code-block table
                                            │    │    ├─ ChartImage → POST to QuickChart → upload PNG
                                            │    │    ├─ CsvAttachment → export_to_buffer → upload CSV
                                            │    │    └─ XlsxAttachment → export_to_buffer → upload XLSX
                                            │    └─ post result_summary + elapsed time
                                            ├─ on timeout:
                                            │    └─ post "⏱️ Query timed out after {n}s"
                                            └─ on error:
                                                 └─ post error_card(db_error)
```

### 5.2 Conversation Context (Follow-up Questions)

When the user replies in the same Slack thread, the bot reads the thread history to build conversation context:

1. Fetch the last ~10 messages in the thread (Slack `conversations.replies` API).
2. Extract the last assistant SQL block (from the proposal card's code block).
3. Include in the AI context: "Previous query was: `SELECT …`. The user is now asking a follow-up."
4. The AI can propose a modified query that builds on the previous one.

**Thread detection:** If the incoming message has a `thread_ts`, it's a reply in a thread. If it has no `thread_ts`, it's a new conversation — start fresh. Always reply in the thread (if the message was in a thread) or start a new thread (if it was a standalone message).

### 5.3 The Approval State Machine

```
                  ┌─────────────┐
                  │   PENDING   │ ← proposal posted
                  └──────┬──────┘
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
     ┌──────────┐  ┌──────────┐  ┌──────────┐
     │ APPROVED │  │ REJECTED │  │ EXPIRED  │ (5 min TTL)
     └─────┬────┘  └──────────┘  └──────────┘
           │
     ┌─────┴─────┐
     ▼           ▼
┌─────────┐ ┌──────────┐
│ RUNNING │ │  ERROR   │ (query failed)
└────┬────┘ └──────────┘
     │
     ▼
┌──────────┐
│ COMPLETE │ → result posted
└──────────┘
```

The state transitions are driven by Slack interactions. Each state is reflected in the proposal message (update the message text/blocks to show the current status — e.g., "⏳ Running…", "✅ Complete").

## 6. Security Model

### 6.1 Query Safety

- **Read-only enforcement:** After extracting SQL from the AI response, classify it:
  - Use `script::split` to detect multi-statement (reject — Slack only allows single-statement).
  - Use `is_read_only_stmt` to reject non-SELECT (INSERT/UPDATE/DELETE/DDL/utility).
  - If the query is not a single read-only SELECT, post an error: "I can only propose read-only SELECT queries in Slack. Open in Tusk to run this query."
- **Row limit:** The AI prompt instructs using LIMIT. Additionally, wrap the query in `SELECT * FROM ({sql}) AS _tusk LIMIT {max_rows_file + 1}` to hard-cap rows (the +1 lets us detect truncation and suggest a file export). This is the same pattern as the grid's `wrapQuery`.

### 6.2 Access Control

- **Channel allowlist:** If `allowlist_channels` is non-empty, only respond to messages from those channels. Otherwise, respond in any channel the bot is in.
- **User allowlist:** If `allowlist_users` is non-empty, only respond to those users. Otherwise, respond to any user in an allowed channel.
- **Approval ownership:** Only the user who asked the question can approve/reject it. Other users clicking the button get an ephemeral error.

### 6.3 Secret Management

- **Slack tokens** (bot + app) stored in the OS keychain (`keyring`), service `"tusk-slack"`, accounts `"bot-token"` / `"app-token"`. Never in config files, never sent to the frontend.
- **AI provider keys** already in keychain (`tusk-ai`). Reused.
- **DB connection passwords** already in keychain (`tusk-profiles`). Reused.

### 6.4 Audit Log

Every Slack-sourced query is logged in the existing query history (`save_history`) with a prefix `[Slack]` and the Slack user's name. This gives full auditability in the Tusk UI.

## 7. Error Handling

| Scenario | Handling |
|---|---|
| No active DB connection | Post: "⚠️ No database connection is active in Tusk. Connect to a database first." |
| Connection lock busy (user is running a query) | Post: "⏳ Waiting for the current query to finish…" — then proceed once the lock is available. |
| AI provider error | Post: "⚠️ AI error: {message}. Check your API key in Tusk settings." |
| AI returned no SQL block | Post: "⚠️ I couldn't generate a SQL query from that question. Try rephrasing." |
| AI returned non-SELECT | Post: "⚠️ I can only propose read-only SELECT queries in Slack. Here's what I generated: {sql}. Open in Tusk to run it." |
| Query timeout | Post: "⏱️ Query timed out after {n}s. Try a more specific query or increase the timeout in settings." |
| Query error (DB) | Post: "❌ Query failed: {db_error_message}" (use the same error surfacing as `db.rs` `From<tokio_postgres::Error>`) |
| Slack API error (posting message) | Log to stderr. The user won't see this — it's a Slack/network issue. |
| Socket Mode disconnect | Auto-reconnect with backoff. Post a status update in the Tusk UI (statusbar indicator). |
| Proposal expired | Update the proposal message: "⏰ This proposal has expired. Ask the question again." |

## 12. Open Questions (flag for review before implementation)

1. **Multi-connection:** v1 uses the active connection. Should the bot be able to switch connections? (Recommendation: no — add a connection picker in settings for v1.1.)
2. **Write queries:** v1 is read-only. Should writes be allowed with a second confirmation? (Recommendation: no — route to "Open in Tusk".)
3. **Multiple Slack workspaces:** v1 supports one workspace (one bot token). Multi-workspace is a v1.1 feature.
4. **Chart library:** QuickChart sends data externally. Should we bundle a native Rust chart renderer instead? (Recommendation: QuickChart with configurable URL for v1. Self-hostable. Native renderer is a v1.1 upgrade.)
5. **Streaming to Slack:** Slack doesn't support streaming text updates natively (you'd update the message repeatedly). The AI response is usually fast (<5s). Is the "thinking…" → full proposal flow enough, or do we want to stream partial SQL? (Recommendation: no streaming — post the full proposal at once.)
6. **Rate limiting:** The bot should handle concurrent messages gracefully (queue them). A simple `tokio::sync::Semaphore(1)` ensures one query at a time. Is that acceptable? (Recommendation: yes for v1.)
7. **Ephemeral vs. persistent messages:** Should the proposal be ephemeral (only visible to the requester) or visible to everyone? (Recommendation: visible to everyone — collaborative teams benefit from seeing the SQL + result. The requester approves.)
8. **`tokio-util` CancellationToken vs. `oneshot` channel:** For clean shutdown. (Recommendation: `tokio-util` — it's a small, well-tested dep.)

## 14. Key Invariants (do not regress)

1. **No query runs without approval.** The approval button is the single gate. Never auto-execute.
2. **Slack tokens never leave the keychain.** Never logged, never in config files, never in error messages.
3. **Query timeout is enforced.** Every Slack-sourced query is wrapped in `tokio::time::timeout`. No unbounded execution from Slack.
4. **Read-only only.** `is_read_only_stmt` + `script::split` (single-statement) guard. Non-SELECT is rejected with an "Open in Tusk" suggestion.
5. **The bot uses the active connection.** If no connection is active, the bot says so. Never auto-connect to a random profile.
6. **Socket Mode acks within 3s.** Slack requires envelope acknowledgment. Ack first, then process. Long-running AI/query work happens after ack.
7. **One query at a time.** A `Semaphore(1)` or queue ensures concurrent Slack messages don't collide on the shared DB connection.
